# Content Platform Architecture Migration

Status: Completed

## Goal

Implement the architecture accepted in the content-systems visual review from migration phase 0 through phase 5 without changing accepted gameplay, balance, player-facing flows, stable content ids, or valid save behavior. The finished project must support ordinary new abilities, statuses, relics, units, floor rules, encounters, campaigns, and rewards through independently authored scenes and immutable resources, with deterministic typed runtime execution, explicit ownership, validated dependencies, versioned persistence, narrow extension points, and measurable conformance gates.

The user authorized continuous execution to completion under an active Codex goal. Routine implementation choices do not return to discussion. Only a genuine authority conflict, incompatible accepted behavior, or unsafe dirty-worktree overlap may stop execution and mark this task `Needs Discussion`.

## Confirmed Architecture

- Concrete heroes, soldiers, enemies, bosses, summons where concrete, items, and relics remain independently instantiable `.tscn` scenes.
- Immutable definitions, bindings, trigger/condition/target/effect/status specifications, tables, project composition, campaign rules, run rules, and presentation profiles are authored `.tres` resources.
- Mutable battle, run, relic, ability, status, cooldown, charge, counter, roll, and save state never enters shared Resources.
- Ability, Relic, Status, Floor Rule, Boss/Encounter, and Reward remain separate product systems. They share typed primitives and deterministic execution, not one universal product lifecycle.
- Reusable authored bindings contain trigger, read-only conditions, target query, ordered effects, rate/usage/recursion limits, and presentation/report metadata.
- Resolution separates pre-resolution modifier, authoritative state-changing effect, immutable resolved domain event, and reactive trigger. Event callbacks enqueue later invocations; they do not re-enter state mutation inline.
- Every invocation and resolved step carries stable chain, source, owner, depth, and sequence attribution plus typed success, skip, failure, or interruption evidence.
- Battle, Run, and Meta are separate scopes. Cross-scope mutation occurs only through validated immutable transition results applied exactly once.
- Authored definitions compile into validated immutable runtime specifications before publication. Missing references, stable-id collisions, category/type mismatches, dependency cycles, and incompatible trigger/target/effect bindings reject the complete publication transaction.
- Runtime instances have one authoritative scope owner and symmetrical activation/deactivation. Success, defeat, timeout, abort, replacement, exception, and disposal clear subscriptions, pending invocations, and mutable instances idempotently.
- Stable ids and versioned DTOs are persistence authority. Live Nodes and shared Resources are never serialized. Migration is incremental, validated before publication, and preserves valid meta progress when an active run is incompatible.
- `GameProjectDefinition` becomes the authored project composition root. `CampaignDefinition` and `RunRulesDefinition` own campaign and run configuration. `RunApplication` remains a stable use-case facade delegating settlement to `RunNodeResolutionService`. `GameRoot` is bootstrap only; `GameFlowCoordinator` owns routing and exactly-once user-flow coordination; screen controllers bind view models and emit typed intent.
- Ordinary recombination of existing primitives is data/scene-only. A genuinely new atomic mechanic has one narrow implementation route consisting of a typed processor/extension, validator, description/report renderer where applicable, and focused tests. Concrete-id dispatch and unrestricted global discovery remain forbidden.

## Execution Sequence And Exit Gates

### Phase 0 — Expansion Gate And Regression Baseline

- Replace validator assertions tied to exact totals such as 8 heroes, 24 soldiers, 13 enemies, or 45 portraits with catalog-derived completeness, identity, category, reference, and one-definition/one-scene/one-portrait invariants. Accepted Alpha target counts remain product facts, not registry architecture.
- Preserve strict validation: duplicate ids, missing scenes/definitions/portraits, mismatched category/definition, invalid required components, and unregistered concrete scenes still fail visibly.
- Establish or retain deterministic battle digests, three current build paths, content fingerprints, isolated scene instantiation, save round-trip/migration, and clean-start baselines before central runtime changes.
- Add conformance fixtures proving an additional valid test content entry does not require changing count constants while an invalid entry still fails with a structured diagnostic.

Exit 0: extra valid test content passes catalog/portrait validation without count edits; invalid identity/reference/category fixtures fail; current deterministic, save, scene-isolation, and playable-path baselines remain green.

### Phase 1 — Typed Effect Kernel And Lifecycle

- Implement typed invocation context, modifier request/result, effect request/result, immutable domain event, reactive invocation queue, deterministic ordering key, chain attribution, typed interruption, and bounded recursion/event/step/rate protection.
- Implement validated authored binding specifications using Godot Resources and focused processors rather than a string action DSL or reflection-driven scripting.
- Establish Battle-scope runtime ownership, subscription handles, idempotent cleanup, queue drain/abort behavior, trace output, and immutable scope transition results.
- Integrate through compatibility adapters and migrate representative existing mechanics end to end without changing their accepted behavior or digest. Presentation and reports consume resolved facts and metadata; they do not become rule authority.

Exit 1: fixed-seed results and digests remain stable for preserved behavior; simultaneous ordering and reentrancy rules are deterministic; all termination paths leave zero scoped listeners/pending invocations/live mutable effect instances; traces explain success and interruption.

### Phase 2 — Ability And Status Products

- Introduce Ability definitions/loadouts/runtime instances for automatic, triggered, passive, and bounded manual-command entry points while preserving current hero command scenes, mana, gold, failure, and presentation contracts.
- Introduce typed Status definitions and instances with explicit source, owner, duration, stacking, expiry, dispel, periodic behavior, and presentation metadata. Only semantics required by current accepted behavior are made authoritative; unresolved future product rules stay extensible rather than invented.
- Replace current generic optional-field growth and concrete runtime branching with composed bindings or narrow typed extensions. Existing concrete content scenes remain independently testable.
- Ensure player descriptions, battle HUD, selected-unit facts, cues, and report labels derive from the same authored specifications and resolved facts where applicable.

Exit 2: current high-reuse hero commands and unit mechanics run through Ability/Status primitives or documented narrow extensions; no concrete-id switch is added; failed commands remain atomic; definitions are immutable across two runtime instances; description/validation/runtime facts agree.

### Phase 3 — Relic Lifecycle And Scope Bridge

- Introduce Relic definitions and per-run/per-battle instance state covering current identity, ownership, stacks, charges, counters, rolls, activation, deactivation, and scope bindings without inventing unconfirmed inventory caps, duplicate rules, rarity curves, or upgrade cadence.
- Migrate every current item modifier/provider behavior to typed modifiers, bindings, or narrow extensions while retaining stable `item_*` ids, independently instantiable scenes, current values, acquisition behavior, and save compatibility.
- Route battle-derived relic outcomes through immutable validated transition results rather than direct Run/Save mutation. Save projection and migration round-trip all mutable relic state that is currently authoritative.

Exit 3: all current items preserve observable behavior and values; battle effects cannot directly write Run/Meta/Save; relic instances activate/deactivate symmetrically, isolate mutable state, and round-trip through save/migration tests.

### Phase 4 — Project Composition, Run Services, Pools, And Encounters

- Author `GameProjectDefinition`, `CampaignDefinition`, and `RunRulesDefinition` Resources that own existing project, region, floor-count, capacity, economy, recovery, reward, node, table, semantic, and presentation references without changing current values.
- Keep `RunApplication` as the public facade while extracting cohesive formation, node resolution, battle preparation, reward/economy, progression, and persistence responsibilities behind typed interfaces where actual responsibility boundaries exist.
- Narrow `GameRoot` to bootstrap only. `GameFlowCoordinator` owns routing and exactly-once user-flow coordination, while `RunApplication`/`RunNodeResolutionService` own the settlement transaction and screen-local controllers own view-model binding plus typed intent.
- Move tower regions, encounter composition, floor-rule references, recruit/loot/reward pools, and Boss phase/timeline references into validated authored resources. Deterministic seeded selection remains authoritative.
- Remove runtime path strings and central concrete-content branches only after their authored replacements are validated and covered.

Exit 4: current three-region/fifteen-floor paths, encounter setup, formation, rewards, economy, progression, saves, and post-battle routing remain behaviorally equivalent; a new test campaign/encounter/pool composes without edits to `GameRoot`, `RunApplication`, `TowerGenerator`, or `BattleSimulation` content switches.

### Phase 5 — Scalable Authoring And Compatibility Removal

- Add focused authored templates and validation routes needed to create a test hero, soldier, ability, status, relic, floor rule, encounter, and Boss phase through existing primitives.
- Add dependency-aware batch validation, clear authored-path/binding-index diagnostics, source guards, deterministic traces, lifecycle leak checks, migration fixtures, and architecture conformance tests.
- Remove compatibility adapters and optional-field authority only when all current content has migrated and no runtime consumer remains. Do not delete user-authored or historical assets merely because a compatibility type exists.
- Validate that recombining existing primitives changes only authored scenes/resources, while a new atomic primitive touches one processor/validator/renderer/test route rather than multiple composition roots.

Exit 5: all current content runs through the target ownership boundaries; ordinary test content requires zero center-code edits; unused compatibility authority is removed safely; full low-concurrency build, automated tests, headless validation, save migration, deterministic paths, and manual smoke handoff pass.

## Non-Goals

- No new gameplay content, balance pass, hero kit redesign, item redesign, encounter redesign, visual redesign, or UI hierarchy change.
- No decision on future ability-slot count, upgrade cadence, relic cap, duplicate policy, rarity curve, corpse economy, resistance model, new combat resource, or other unresolved product rule.
- No rename of stable content ids unless an existing accepted authority already requires it.
- No multiplayer/network synchronization, ECS rewrite, dependency-injection framework, universal scripting language, reflection DSL, unrestricted global event bus, visual node editor, or behavior-tree platform.
- No runtime dependency on `D:\godot\rpg`, no donor-runtime transplant, no publishing/hosting work, and no changes to `web/game-mechanics-atlas/`.
- No cleanup, rollback, deletion, formatting, or commit of unrelated dirty-worktree changes.

## Constraints

- Remain on `main`; do not create, switch, or recreate a local development branch.
- One write-capable execution Agent owns the migration. Independent verification Agents are read-only unless the main Agent explicitly authorizes a focused correction after findings are reported.
- Preserve all existing user and prior-task changes. Before editing an overlapping file, inspect its current diff and integrate rather than overwrite.
- Prefer authored `.tscn`, `.tres`, component scenes, typed Resources, and typed signals. Code loads, binds, validates, compiles, and executes them; it does not build whole content/UI trees ad hoc.
- Preserve current independent scene contracts and mutable-state isolation. New content scenes cannot depend on hidden level/UI/autoload nodes.
- Preserve deterministic fixed-tick authority, navigation/movement rules, formation, battle reports, UI input behavior, `RealmTheme`, semantic icons, animated portraits, and the current `1600×900`/`1280×720` presentation contract.
- Preserve valid version-3 saves where the schema need not change. If a mutable persisted field is genuinely required, increment schema explicitly, implement incremental migration, isolate test paths, and preserve valid Meta/Settings on active-run failure.
- Use low-concurrency builds (`dotnet build -maxcpucount:2 -v:minimal`), static checks first, and only the minimum Godot/headless launches needed for phase gates. Never terminate user Godot/editor/game processes.
- Do not silently relax validation to pass tests. Invalid content must fail before registry publication with structured, low-noise evidence.
- If a phase exposes an actual authority contradiction or requires a new product rule, stop before implementing that decision, record the conflict and safe resume point here, and return to discussion. Ordinary local design choices do not interrupt execution.

- All six phase exit gates pass and their evidence is recorded in this document.
- Accepted gameplay, presentation, deterministic movement, battle results, run progression, values, stable ids, and valid save behavior remain unchanged except for explicitly documented schema migration necessities.
- The accepted target architecture is represented in authoritative system documentation and actual runtime ownership, not only in the review HTML.
- Content validation derives completeness from authored catalogs and dependency contracts rather than exact sample totals.
- Definitions, compiled specifications, runtime instances, transition results, and save DTOs have explicit owners and do not leak mutable state across layers.
- Ability, Status, Relic, Effect, Trigger, Condition, Target Query, Floor/Encounter, Run service, and persistence responsibilities are separately testable.
- Typed deterministic effect resolution, queue/reentrancy rules, loop budgets, source attribution, lifecycle cleanup, dependency compilation, schema migration, causal traces, and conformance tests are executable gates.
- All current content uses composed primitives or narrow documented typed extensions without concrete-id behavior dispatch.
- `GameProjectDefinition`, campaign/run-rule resources, cohesive Run services, `ScreenRouter`, `GameFlowCoordinator`, and immutable Battle→Run→Meta bridges own the approved target boundaries.
- A clean low-concurrency .NET build, focused unit/contract tests, Godot headless content validation, save migration/round-trip, deterministic battle paths, and player-flow smoke tests pass.
- An independent sub-Agent reviews scope, architecture conformance, code diffs, and verification evidence; its findings are either fixed and reverified or explicitly recorded as unresolved authority blockers.
