## Goal

- Unreal GAS-inspired base/current attributes, sourced modifiers, typed magnitude inputs, and presentation cues;

## Confirmed Architecture

### Separate Products, Shared Execution Vocabulary

Ability, Status/Modifier, Trait, Equipment, Relic, Tactical Command, Floor Rule, Encounter, and Reward remain separate authored products with separate lifecycle owners. They may reuse:

- stable source identity;
- typed conditions and target queries;
- typed magnitude inputs;
- attribute modifiers;
- authoritative effects;
- typed resolved events and reactive bindings;
- deterministic ordering, limits, traces, and presentation cues.

Do not collapse them into one universal product class, arbitrary scripting language, reflection dispatcher, string action DSL, or global content switch.

### Immutable Definitions And Mutable State

- Authored `.tres` definitions and compiled records are shared and immutable.
- Mutable health/resources, attribute modifiers, status stacks/durations, ability cooldowns/uses, trait activation state, equipment projections, relic counters, tactical points, and subscriptions belong to explicit Run or Battle scopes.
- No mutable runtime fact may be written into a shared Resource.
- Concrete heroes, enemies, temporary units, equipment/relic items, and tactical commands remain independently instantiable authored scenes where the project contract requires concrete content scenes.

### Attributes And Modifiers

Each battle unit owns one mutable `BattleAttributeSet` created from immutable compiled base attributes. The minimum initial attribute vocabulary is:

- `MaxHealth`, `AttackDamage`, `SpellPower`, `AttackSpeed`, `Armor`, `MagicResistance`;
- `AttackRange`, `MoveSpeed`, `CriticalChance`, `CriticalDamage`;
- `MaxMana`, `StartingMana`, `HealingPower`, `LifeSteal`, `ControlResistance`.

Current health, current mana, shield, cooldowns, position, and targeting are runtime resources/state rather than ordinary base attributes.

Modifier evaluation is deterministic:

1. base value plus ordered additive contributions;
2. multiplied by all multiplicative factors;
3. one deterministic override winner when present;
4. attribute-specific clamp.

Every contribution carries a stable `CombatSourceRef` plus instance identity and application ordering. Removal by source must be authoritative and reversible. Same source refresh/replacement and different-source stacking are explicit, not inferred from display text.

Typed magnitude inputs initially include constant, source attribute, target attribute, invocation/context value, team persistent/deployed/alive count, and trait value. Snapshot-versus-live capture is explicit. New atomic calculations use a narrow registered processor and compiler validation; no arbitrary expression parser is authorized.

### Battle Combat Pipeline And Events

Ordinary attack, movement, lethal resolution, and outcome remain owned by `BattleSimulation`; they are not reimplemented as fake Abilities. The simulation exposes deterministic typed phases modeled after mature modifier hooks:

- battle started/completed;
- attack declared and attack landed;
- ability resolved;
- damage/healing/shield resolved;
- status applied, stack changed, and removed;
- unit summoned, moved, defeated, and killed.

Pre-resolution calculation accepts typed modifier requests. Post-resolution events are immutable facts and may only enqueue later work through the existing bounded deterministic queue. They cannot synchronously re-enter the authoritative mutation currently resolving.

The combat pipeline is Battle-scoped pure C# infrastructure, not a global Autoload EventBus. It must dispose every subscription and pending invocation on victory, defeat, timeout, abort, replacement, exception, and disposal.

### Status / Modifier Product

Buff and Debuff are one Status/Modifier product. Presentation, dispel category, state tags, and harmful/helpful classification distinguish them.

Each compiled Status supports:

- instant, timed, or permanent duration;
- aggregation by source, aggregation by target, or independent instances;
- stack limit and overflow response;
- duration refresh and periodic reset policies;
- periodic interval and periodic effects;
- ordinary/strong/non-dispellable categories;
- removal reason and death policy;
- granted state/gameplay tags;
- sourced attribute modifiers;
- typed lifecycle/reactive bindings;
- immutable presentation metadata.

Runtime identity includes definition, source, owner, application sequence, stacks, applied/expiry/next-period ticks, and captured magnitudes. Multi-source shared stacks must be representable; the current `(definition, source, owner)` key cannot remain the only aggregation policy.

Control effects grant typed state tags queried by action authority. Control resistance modifies authored control duration under one documented rule. Permanent and temporary attribute changes use the same reversible modifier authority.

### Traits / Synergies

TFT-style `TraitDefinition` is authoritative:

- stable id, player-facing identity, icon/presentation;
- explicit contribution/counting policy;
- ordered breakpoints with `MinValue`, `MaxValue`, display style, and compiled effect loadout.

Heroes and explicit equipment/emblems expose typed `TraitContribution` values. String gameplay tags may still support targeting and semantic display but do not constitute an active trait system.

One team-level Battle trait scope calculates the current contribution snapshot, selects the active breakpoint, removes the previous breakpoint source, and applies the new breakpoint source using ordinary modifier/status/ability/reactive primitives. Trait-specific Battle switches are forbidden. Temporary-unit contribution, duplicate identity, deployment-only counting, and explicit extra contribution are data policies.

Run-level trait snapshots may feed offers and the hidden `30`-value achievement. `30` is a trait value, never a requirement for thirty physical bodies.

### Equipment And Relics

Equipment is owned by a concrete persistent hero instance. A configurable slot capacity is authored in Run rules; the first production contract uses the mature TFT default of three slots. Equipment may grant sourced attributes, Abilities, Statuses, reactive bindings, and Trait contributions to its owner.

Relics remain Run-level content. Static relic modifiers become ordinary sourced Battle modifiers/effects. Reactive relic definitions subscribe only to typed events they require and own explicit Battle or Run counters with threshold, consumption, and reset policy. The fixed `RelicBattleModifierKind` enum may remain only as a temporary migration adapter and must not be the final extension route.

Existing production item classification and balance remain unchanged until a separately documented content classification says which concrete items become hero equipment. This migration must nevertheless include one independently authored production-safe equipment vertical-slice asset and prove ownership, save, battle projection, removal, and isolation.

### Unified Hero Roster And Population

- Every persistent recruitable player combatant follows one roster-hero instance contract and costs one population.
- The starting hero is the first roster entry, not a special commander runtime category.
- Current population is persisted and limits deployed persistent heroes.
- Ordinary population cap is `10`; explicit sources may raise effective cap up to physical ceiling `18`.
- Temporary units consume physical cells but not persistent population and cannot keep the player team alive after all persistent heroes are defeated.
- Exact long-term reserve tuning remains authored data. Preserve the current reserve allowance as a compatibility default; do not present it as a permanent design landmark.
- Exact population reward cadence remains balance/content work. The architecture must expose validated deterministic population grants and above-cap sources without inventing a final reward schedule.

Active-run schema advances from v3. A v3 run migrates only if every current player combatant and formation identity can be represented losslessly. Otherwise reject the active run explicitly while preserving Meta and Settings. Never silently discard a roster member, item, formation cell, or health fact.

### Independent Tactical Commands

- Commands are compiled independent content, never a required child/component of one hero.
- Run state owns exactly two equipped command stable ids.
- Each battle starts with exactly three shared tactical points.
- Commands may cost one to three points and retain typed cooldown, maximum use, target, effect, and atomic preflight rules.
- Failure consumes no points, currency, cooldown, use, or partial mutation.
- Existing useful command Resources/scenes may be adapted without stable-id content dispatch.

### Presentation Cues

Simulation emits typed presentation cues separate from gameplay mutation. The first cue lifecycle supports `Executed`, `OnActive`, `WhileActive`, and `Removed`. Status UI, VFX, audio, damage/healing numbers, selection, and report presentation bind immutable facts/cues; they do not inspect runtime product classes or infer rules from prose.

## First Vertical Slice

The architecture is not accepted on fixtures alone. One production-safe Frost/Freeze attack-speed slice must prove the full path:

1. one hero-owned equipment effect gains attack speed from that hero's attack-landed events;
2. an attack applies shared-target Frost stacks with correct source attribution;
3. reaching an authored threshold consumes/changes Frost and applies timed Freeze;
4. Freeze grants the action-disabled state and obeys control resistance;
5. one TFT-style trait breakpoint modifies a Frost/attack behavior through ordinary shared primitives;
6. active/stack/removed presentation facts and cues are visible without changing simulation authority;
7. same-seed battle result, event ordering, trace, and cleanup are deterministic;
8. no concrete hero/equipment/trait/status id appears in `BattleSimulation`, generic scopes, Run services, or UI dispatch.

This is an architecture proof, not final Frost balance or a complete elemental roster.
