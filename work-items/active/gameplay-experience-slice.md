### 玩家走过的过程

| 阶段 | 玩家在做什么 | 必须看见的反馈 |
| --- | --- | --- |
| 预置休整点 | 看一支已有基本职责的四人队伍和下一战威胁 | 明说这是试验起点，不虚构一场已发生的胜利或战报 |
| 第一份奖励 | 三选一遗物，选择一种强化方向 | 哪些英雄能受益、需要什么条件；无满足者时明确显示 |
| 招募与准备 | 三选一角色，可跳过；安排新角色和站位 | 候选现在能做什么、补什么短板，不要求玩家先懂体系名 |
| 第一战 | 观察真实自动战斗，可暂停、调速、使用两个既有战术命令 | 看见承伤、攻击／控制、关键效果与归属 |
| 战报与再选择 | 查看结果，再三选一装备并指定装备者 | 装备前后有效属性／规则差异，而非单个总战力分数 |
| 再次准备 | 根据下一战预告调整位置和装备分配 | 明确此次改变了什么；不自动替玩家改阵 |
| 第二战与回顾 | 检验调整，回看两次选择，也可回到检查点换方案 | 真实战报、选择历史、重试入口；不凭两场数字差宣称因果 |

胜利按既有规则推进；失败或超时先展示真实战报，然后允许回到试验检查点，不伪造获胜以进入奖励。两战完整体验暂以 10–15 分钟为目标，不是已经测得的时长。

### 不再把系统全部推给用户决定

| 设计维度 | 第一版基线 | 为什么这样选／边界 |
| --- | --- | --- |
| 决策密度 | 一次主要处理一个问题：遗物方向、角色职责、装备归属 | 不把商店、刷新、升阶、合成和路线同时塞进一屏 |
| 角色价值 | 初始队伍可独立战斗；候选到手就有用途 | 不用一个指定稀有角色作启动钥匙，也不把每个角色宣传成核心 |
| 构筑路线 | 内容至少覆盖集中输出、范围处理、持续作战三种不同需要 | 这是验证覆盖，不是三个强制职业／元素体系；允许跨方向组合 |
| 状态与兑现 | 状态本身只做明示的事；额外输出来自明确的读取者和兑现者 | 不因为用了防御、治疗或某元素，就自动获得没有写出的伤害 |
| 遗物 | 局内持有，可以作用于多人；条件、受益者、上限明确 | 不把团队来源等同于全队无条件等额强化 |
| 装备 | 归属于具体英雄；保留现有三槽契约 | 先做获得、指定所有者、替换／转移的完整交易，不做任意内容库免费生成 |
| 调整成本 | 试验准备阶段允许已有装备无损转移；战斗内锁定 | 这是待体验的试验规则，不是已确认的正式装备经济；槽位及未选择奖励仍是机会成本 |
| 供给 | 固定、有限且可审计的候选组；每组至少有即时功能选择 | 先检验选择本身；不偷偷采用此前 Web 的职责保底提案，也不据此证明随机池可达性 |
| 数值成长 | 本段主要来自一次招募、遗物与装备 | 暂不再引入等级／技能点／合成货币，避免无法识别是谁带来变化 |
| 人口 | 沿用现有起始人口 7、每英雄 1 人口、普通上限 10／物理上限 18 | 第一段四人起步，最多招一人；不以此宣称人口成长曲线已经验证 |
| 信息 | 奖励选择前可看队伍和下一战的主要威胁 | 不给伪精确胜率；不能等玩家投入后才披露关键免疫或触发限制 |
| 敌人 | 第一战考验基本职责，第二战改变一个主要威胁维度 | 不用全体系免疫迫使唯一解；不同时大改血量、场地、敌群和规则 |
| 持续性 | 跨战生命／死亡恢复遵循现有规则；状态与战术点按既有作用域重置 | 不额外偷偷满血，避免掩盖续航价值；起点伤势可作为后续独立变量 |
| 路线与商店 | 第一段固定顺序，不做完整随机地图和商店 | 后续单独验证资源投入与风险选择；本段不能替经济玩法背书 |
| 失败解释 | 先给事实：谁受益、谁没能行动、何时倒下、效果是否发生 | 不把“伤害低”直接解释为“角色弱”，不让分析标签创造战斗事实 |

上述规则不按角色素材倒推；具体内容绑定前必须能说明其职责、输入、受益者、代价和在两场战斗中的可观察结果。优先适配现有可独立实例化的内容；缺少机制时记录缺口，不能静默用无关加属性物品顶替。

## 如何让用户容易调节，而不是做另一张表单

正常游玩只展示当前选择和后果。试验工具收在独立入口，不压在战斗主视图上。

- **从同一起点换一个选择：**保留原分支和选择前检查点，创建新分支；原记录不覆盖。固定初始队伍、生命、装备实例、候选、敌人、场地和种子。
- **从第一战后再试：**保留这一战的真实结果和跨战状态，只替换之后的奖励／装备／站位，再打同一第二战。
- **切换挑战：**同一队伍换敌方威胁属于另一个实验，单独标记，不能混称奖励 A/B。
- **调节数值：**后续开放小范围参数覆盖，每次开始前生成不可变配置快照。战斗运行中不热改权威数值，不修改共享 .tres。

同种子不等于所有反事实随机事件一一对应：方案改变可能改变事件顺序及随机调用。记录命令时机和目标、配置版本与实际结果；若战术操作不同，标成混合变化，不宣称只由奖励导致。两场不同敌人的输出差也不直接相减作收益。

第一轮用户只需指出“这里不知道为什么”“这个选择看不出区别”“我想改但没有办法”。Agent 负责根据记录定位规则、内容、信息或数值问题，不要求用户先回答专业分类。

## 现有实现可复用与缺口

本轮只读核对：

- `src/App/GameRoot.cs` 已负责发布内容和启动 `GameFlowCoordinator`；`AppScreenHost` 已组合招募、奖励、部署、真实战斗、战报等 authored 场景。
- `src/Run/RunApplication.cs` 及现有服务可复用编队评估、战斗准备、战斗结算和已有遗物发放；`IRunSaveService` 提供注入隔离存储的边界。
- `BattleSimulation` 是唯一战斗权威；试验不得加模拟胜负或另一套伤害结算。现有 Battle Lab 只覆盖配置与战斗，不能把它误称完整成长切片。
- **奖励链缺口：**`RunRewardEconomyService.BuyItem/GrantItem` 当前仅接受 Relic；不能把现有战利品屏直接叫作装备分配流程。
- **装备交易缺口：**`RunEquipmentService.Equip` 按内容 id 新建实例并替换槽位，`Remove` 删除槽位实例；这不是带库存、转移及机会成本的玩家奖励交易。需要明确持有实例、获得来源、唯一归属、被换下装备去向，再接入真实输入。
- **记录缺口：**现有战报有实际伤害、治疗、生存等，不应先假定已具备所有遗物触发／拒绝／转换的可见归因。只按需要接入已有事实，缺少事实时明确未记录。
- **流程缺口：**现有随机爬塔不是固定切片脚本；需要 authored 阶段配置与独立 session，不靠直接修改 ActiveRun 字段跳过正式结算。

这些是实现范围，不要求用户重新选择。不得借补缺口改写正式装备经济或生产存档支持范围。

## 实现顺序与验收

### S1 — 设计基线与复用核对（本轮完成）

### S2 — 独立 session 与完整最小循环（下一执行节点）

1. 只读内容绑定：挑选有明确职责的初始四人、三种候选英雄、三件遗物、三件装备及两个威胁包，逐个验证实际编译效果。内容不足时补必要原子机制，避免围绕现成元素倒推方案。
2. authored 试验定义持有版本、阶段、候选、初始队伍、敌人、场地、种子和参数；可变状态、检查点、选择记录独立持有。优先复用 Run 命令；新增适配只负责流程与注入，不改战斗内核。
3. 独立试验入口不依赖或加载生产 ActiveRun／Meta。先采用仅内存会话与深拷贝检查点；退出前说明未导出试验将不保留。需要跨次保存时只使用独立版本化试验路径，不复用生产存档目录。
4. 接通遗物领取、招募、布阵、第一战、战报、装备领取与归属、第二战、结果。每个奖励只能领取一次；失败不能假装成功进入下一阶段。
5. authored UI 保持现有 Theme 与交互契约；显示当前阶段和少量关键反馈，不把专业配置工具当默认入口。

### S3 — 比较和真实输入验证

- 同起点重试与战后检查点重试可靠；旧分支不会被新尝试覆盖。
- 行为测试覆盖重复领取、无效目标／槽位、装备唯一归属和替换、失败不消费、战斗重复结算、退出清理、共享定义不变、真实存档路径无读写。
- 低并发构建和必要的现有 Godot 测试入口；不新装框架，不无差别跑完整爬塔回归。
- 实际鼠标／键盘完成关键选择、装备指定、布阵、战斗／战报及重试；查看渲染，自动调用事件不能冒充交互验收。工具不足时明确未验收项。
- 用户试玩验收的是是否看懂、想不想换个选法、能否感到差别，不要求先阅读此技术文档。

### S4 — 按体验结果扩展

先修第一段暴露的问题，再增加缺件补救、资源／路线取舍、转型和成形后挑战。通过固定样本之后才测随机供给；不能以样本能通关证明随机局可达或全体系平衡。采纳规则时再同步玩法权威与模型记录。
