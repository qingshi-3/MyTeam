# R02 英雄培养：方案讨论

## R02-Q01：专属机制升阶的获得与选择结构

状态：UP01–UP05 的可接受空间与成本约束已由 [R02-D01](decisions.md)确认未合并，具体采用范围仍待讨论。以下保留原推荐，其仅选 UP01 的范围未被用户整体采用。来源、UP01–UP06 与初期兼容边界见 [已有证据](evidence.md)。R01-D01 机制升阶为主、允许不培养羁绊单位已定；本轮不定材料、品阶数或回收，也不将平衡提醒转为新规则。

### Q01-P01：初期采用英雄专属的预设升阶路线

Agent 建议 UP01：每个英雄各品阶的专属机制加强预先设计，玩家投入资源即可取得该阶结果，不再抽取该英雄的强化，也不在升阶时选择技能分支。玩家的决定集中在培养哪个英雄、何时投入和停在哪阶；同英雄同品阶的本体加强相同，阵容、羁绊、装备与遗物继续提供差异。

这与用户固定本体、费用＋品阶和机制升阶方向较为连贯，也便于拿到低费英雄时理解其核心潜力。代价是同英雄的本体成长不承担随机分支变化；如果用户希望这种变化主要发生在英雄升阶本身，则 UP03／UP04／UP05 更符合该目标，但需要明确扩大 M01 的本体选择范围。此处并非用旧决定禁止新讨论。

UP02 独立主被动投资可保留另一结构，初期不建议为每个英雄增加多条进度；UP06 保留特殊条件／后续进化参考。不规定固定几阶、每阶只加强一个技能、数值完全不变或所有英雄同一升级模板。原作三选一、三节点、两次能力升级均未采用。

### 恢复与依赖

初提案时尚无用户决定；后续 R02-D01 已认可 UP01–UP05 的可用空间，未整体接受此处只用 UP01 的推荐。继续按已确认边界讨论真实未定的成长节点或资源问题，不立即枚举正式英雄技能。I24 跟踪与费用、成长、回收的关系，I15 衔接固定主动＋被动与专属成长选择；任何新选择结论只进入讨论区，统一整合前不改权威和实现。

## Q01-P02：复用成长内容与选择规则，控制逐英雄制作成本

日期：2026-09-08。性质：回应 R02-D01 的 Agent 方案建议，未获单独采用。用户关注系统实现与业务配置成本，不要求本轮实现；仅只读核查相关系统和类型。

### SY01：把强化内容与如何获得分开

建议每项专属加强作为有稳定身份的内容条目，说明适用英雄、前置节点、互斥／累积关系、提供的机制和说明。固定路线、主动／被动轨道、分支与随机候选引用同一类条目，不各自复制一套效果。

| 结构 | 主要变化放在哪里 |
| --- | --- |
| UP01 固定路线 | 指定下一项，满足条件后直接取得 |
| UP02 分别投入 | 条目归入主动／被动等轨道，各自记录前置和投入 |
| UP03 固定专精 | 明确候选集合，选择一项并排除互斥项 |
| UP04 混合路径 | 多次机会记录路径投入，以前置和深层节点要求控制混合 |
| UP05 随机候选 | 从合格集合生成候选，再使用共同选择与取得流程 |

这些不是五套战斗系统。共用可以涵盖资格、支付、取得、保存与展示；每种模式仍有自身资格及失败场景需要实现。轨道、互斥组与候选规则应只增加实际所需部分，不先建立任意图脚本编辑器。

### SY02：复用效果与机制表达，不为每位英雄复制处理器

同一项“治疗后向目标附加护盾”无论固定获得、专精选择还是随机候选选中，其战斗规则应相同。采用事件／条件／目标／数值或计数／结果的共享组合表达，例如来源限定、目标查询、施加状态、造成伤害、治疗、护盾和次数间隔；每项效果仍保留自己的来源与清理语义，不混并所有系统生命周期。

独特玩法来自组合和关系，不要求每名英雄专有一段运行代码。确实缺少通用能力时，新增命名清楚、边界明确、可复用的能力后供内容引用，而不是按英雄 id 分支。也不强迫所有新想法都用现有原语勉强拼出失真的效果。

注意：此前“溢出治疗转盾”依赖溢出量，现有 EventEffectiveValue 是实际生效量，不能偷换为溢出治疗。需要核实／补充对应事件数据才能支持该语义；这是新增通用能力的例子，不是当前已完成效果。

### SY03：控制配置维护成本，不能只是把代码搬进巨型配置表

基础英雄只维护一份，各阶引用独立加强，不为每阶复制完整英雄、主被动、装备与表现定义。复用的是可解释的机制模板／资源组合，英雄专属适用范围仍独立声明；不同内容的可变状态必须按实例归属。

避免让内容作者反复填写底层字段；常见机制可提供少量有意义的参数、继承默认值与引用预览，允许特殊内容组合共享组件。初期可先沿用现有 Resource／编译流程和小型模板，不默认新增完整可视化编辑器。选择互斥、前置无法到达、重复授予等问题应尽量在发布前给出具体内容位置的诊断；数值与描述同步、机制变化的前后对比可逐步辅助作者，不能承诺说明自动生成即可代替人工核对。

### SY04：机制新增与接入新增分别记成本

只读 [内容契约](../../../../system-design/content-composition-foundation.md)、[系统架构](../../../../system-design/tower-autobattler-architecture.md)、[AbilityDefinition](../../../../src/Abilities/Authoring/AbilityDefinition.cs)、[AbilityLoadoutDefinition](../../../../src/Abilities/Authoring/AbilityLoadoutDefinition.cs)、[EffectStepSpec](../../../../src/Effects/Authoring/EffectStepSpec.cs)、[RunOfferDefinition](../../../../src/Project/RunOfferDefinition.cs)、[RunOperationDefinition](../../../../src/Project/RunOperationDefinition.cs)后可区分：

- **已有可复用基础**：类型化触发、目标查询、条件／公式、状态和效果授予及撤销、编译验证、来源隔离；RunOffer 有固定／池候选、条件成本收益和保存事务的既有模式。
- **仍需设计和接入的成长公共层**：升阶条目／路径进度、选项互斥、英雄实例取得结果、升阶资源支付、持久化与战前有效能力组装。已读 RunOperationKind 没有专属升阶操作；普通 Offer 也不意味着当前已支持所有路径规则。
- **按内容需要补的能力**：技能机制差量或受约束的版本替换、特定事件读数、独特范围／计数等。已有 ReplaceGrants 不等于可随意热改任何技能字段；共享静态定义不能写入局内成长。

具体使用差量修改、受控版本还是授予组合应按代表性内容比较，不在本轮定一种万能方案。不能据资源类存在就声称机制升阶已实现，未运行或验证。

### SY05：用少量代表内容检查成本，不先要求支持全部形式

后续获授权实施前，可先用固定授予、互斥选择、混合路径和随机候选引用同一项加强，检查获得与效果是否真正分离；再用需要新读数的机制检查扩展是否能保持通用。此为成本审查方法，不是已制作样例或自动验收。

重点观察新增一个英雄为什么需要改运行代码、同一机制是否在多处重复配置、改基础技能是否要同步修改多个版本，以及作者能否看清前置和实际结果。独特机制需要新增实现本身不算失败；应区分真实的新能力与本可复用却重复编写的逻辑。无需先定“支持所有结构”或虚构配置耗时数字。组合越多仍有内容设计、表现、教学及验证成本，系统复用只能减少重复劳动，不能消除这些工作。

### 用户回应与恢复

R02-D01 已确认 UP01–UP05 都可接受且重视成本；不再等待只采用 UP01 的表决。下一步先把共享方式、已有能力与缺口整理清楚，按真实需求决定初期范围；不另起工程任务或全面技术设计，不要求用户再确认允许有升阶选择这一范围。UP06 原定位保持，资源／节点数量与回收继续未定。

### 用户补充：复用不能损害设计特色

2026-09-08 用户强调尽量复用，不能生搬硬套导致设计没有特色，已补入 R02-D01。SY01–SY05 不是压缩英雄差异的模板要求，也未整体获采用。先明确期望的玩法，再判断哪些部分有真实共性；确需新机制时可扩展，不要求它先被多个英雄使用。专用能力应有清楚职责及生命周期，但不必为了泛化增加无用配置层。

成本约束依然有效，不能反向解释成所有内容都应独立重写。后续进入真实未定的成长问题，不反复将复用原则或一般工程取舍交给用户表决；当前不实现。

## R02-Q02：英雄升阶的支付资源与适用范围

日期：2026-09-08。状态：后续 [R02-D02](decisions.md)已确认 UR01＋UR03 并存，以下保留初次推荐，其范围未被整体采用。完整比较及来源见 [UR01–UR07](evidence.md)。不要求重新审批核心集中培养、UP01–UP05 或一般复用判断。

### Q02-P01：以可自由分配的英雄培养资源为基础

Agent 推荐 UR01：初期使用全队共享的英雄升阶资源，由玩家决定投给谁。倾向先与金币区分，使英雄机制成长有相对独立的预算，而不是每次都与招募、换装、刷新抢同一笔钱。这个独立性是推荐，尚未获用户确认；与装备是否共用材料也未决定。

理由是用户希望开局随机招募、低压力下探索体系、遇到关键装备／遗物后逐渐定型，也允许低费养核心和后期换核心。拿到英雄后可调度手中未用资源，比等待同名、职业材料或该英雄个人经验更直接支持这些目标；已投入资源能否回收仍由 R03 决定，不推定无损替换。

UR02 同样能自由指定英雄，主要代价是共用经济预算；UR03／UR04 会让职业材料或重复供给更积极地引导成长，也会额外限制已选核心的可达性。这些有真实玩法价值，完整保留，不因推荐 UR01 而省略。初期不建议把 UR03／UR04／UR06 再叠成所有英雄的必经门槛；UR05／UR07 按原后续继承／条件成长范围保留，未恢复为初期系统。

本建议不规定全英雄同价、每阶同价、全部升满、英雄材料与装备共用、无限购买材料、金币兑换比例、Boss 专属材料或确定成功。共享资源只说明未投入时的归属和适用对象；具体培养结果仍可按 D01 保持各英雄特色。

### 后续衔接

先处理用户对资源基础及限制的回应，再进入 R03 培养回收所需的投入归属；资源来源／产量／兑换归 R08／R09，个人资格与阶段窗口若采用再关联 R10。无需在本题决定完整经济数值。I24 记录这些依赖，M05 的 I21 仅作装备侧相邻结论。

### 用户回应：UR01＋UR03 并存，材料帮助路线规划

用户认可共享培养资源与职业／羁绊材料组合，明确类别材料可引导路线规划、丰富战斗外玩法，已记录 R02-D02。原推荐对 UR03 的初期限制不再作为当前方向；资源自由分配与类别导向都应保留其作用。下一步聚焦两类资源的支付关系，不先假设共同必付、任意互换或具体材料路线，不自动采用同类英雄供体。材料供给与路线衔接归 R08／R09／R10，预告与回收分别关联 R12／R03。

## R02-Q03：通用资源与类别材料怎样共同参与升阶

日期：2026-09-08。状态：后续 [R02-D03](decisions.md)已采用 PY01 替代／混合支付。以下保留初提案及取舍，供给补偿方式和具体数值未随支付关系一并确定。D02 的 UR01＋UR03 保持；原作依据与项目推演分开。

### Q03-P01：优先考虑替代／混合支付，让类别路线提高培养效率

Agent 推荐 PY01：对匹配类别的英雄，两类材料可以支付同一升阶投入，并允许混合补足；未用通用资源仍可保留给其他英雄。同等路线投入下，倾向让类别资源以更充足的供给或更高的适用培养价值补偿用途限制，使路线选择产生“灵活性与目标培养效率”的取舍。此供给关系是推荐的成立条件，不是已定掉落量或兑换比例。

理由：保留用户期望的前期探索、逐渐定型与后期替换空间，同时让玩家为当前体系主动选择有匹配材料的路线。只走通用来源可能培养效率较低，走类别路线则承诺其适用方向；不需要把某次材料缺失直接变成所有相关英雄的升阶禁令。

如果用户希望路线决定关键专属加强能否获得，PY03 的阶段门槛比 PY01 更符合该目标；若每次培养都应受类别路线约束，则 PY02 更直接。这是不同体验，不以“有门槛就是坏设计”否定后两者，也不把原装备“未升级仍可推进”扩大成英雄材料无门槛要求。

PY04／PY05 提供不同资源用途，但会改变成长内容或选择控制结构，初期不建议仅为了安置类别材料新增这些层次。它们仍保留可用比较，不推定用户否定。D01 的各英雄特色优先保持。

### 恢复与跨题影响

先处理用户对 PY01–PY05 的回应，再明确真正影响投入归属与回收的未决点。具体类别、双羁绊适用范围另聚焦；供给、兑换、预告和回收分别归 R08／R09／R10／R12／R03。I24 跟踪当前状态，未新增决定或实施任务。

### 用户回应：先采用 PY01 混合支付

用户选择 PY01，记录 R02-D03；基础支付关系收束。通用与匹配类别材料可替代、混合支付同一次升阶，支付组合不额外改变加强或选择规则。换算、类别适用、供给及回收仍未定，原示例数字与奖励效率建议不自动成为决定；PY02–PY05 保留原比较，不继续作为当前待表决套餐。后续先核对实际影响投入归属的类别边界，再衔接 R03，不重复确认混付方向。
