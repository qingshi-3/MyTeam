# R07 招募机制

进程状态与当前讨论点见 [总览](../../../roadmap.md)，不在此重复维护。

## 决策边界

- 要决定：何时出现英雄选择、刷新/保留/跳过/重复候选/定向补救如何运作。
- 不涉及：不代替 R06 的池定义，价格量级与 R09 联动，不默认共享牌池或利息。
- 前置或协作依赖：R01、R04、R05、R06
- 本议题期望产出：招募决策、失败补救和与阵容的接口。

## 已有跨题决定

[R05-D01](../../roster-and-growth/population/decisions.md)已明确普通部署容量默认开放，实际阵容增长由节点招募控制：部分战斗后可选一名英雄加入，商店／招募兵营可消耗资源刷新候选，并有该次机会最多招募 x 名的限制。具体 x、候选数、刷新费用／限次、招募费用及满员处理待本题与 R08／R09 衔接，不重新表决独立人口升级。刷新不自动重置该次招募总额度；细节决定只在所属决定文件维护，见 I26。

R06-D01 的组随机英雄池与 G03-D02 的适配推荐／其他体系空间是前提。普通同名制度依 R07-D01；特殊复制的贡献与受益按内容与 M03 衔接，见 I16／I28。不能从参考云顶或现行配置默认值重新推定普通重复英雄。

同节点候选保留与跨节点预约分开，刷新不能新增招募名额；Q02 的相关限制和供给接口见 I29。

## 阶段衔接

R07-D01／D02 足以衔接 [R08 商店与奖励](../shops-and-rewards/README.md)。剩余开局候选／选择数量、阶段档次和费用、节点频率、降权参数属于实际供给／经济设计；RF02–RF06 属遗物内容，不继续逐项表决。满员、候选不足和退出后再招募仍需 R04／R03／R08／R09 协同，见 I25／I28／I29，不默认为已解决或固定回收规则。若后续具体流程出现真实制度冲突，再回到本题；当前不新增招募决定。
