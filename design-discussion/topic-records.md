# 议题记录约定

这是写作约定，不是待填写的空表单。必要信息缺失时先补证据或留下待定，不阻塞普通阅读整理。

## 先展开机制，再由用户判断

2026-09-06 用户纠正讨论方式：已有大量游戏调研，不接受只给 ABC 粗粒度方向；只要机制不同且与当前问题相关，就应列出，由用户思考决定。

用户随后明确认可 G02-Q01 的呈现方式：聚焦一个真实的全局机制问题，逐项提供具体操作过程及差异，既不分散也不过度抽象。后续沿用这一粒度；对表达方式的肯定与对具体方案的采用必须分开记录（该轮实际选择初期无介入，而非 Agent 推荐的保留独立指令）。

- 先写清本次问题、已定边界和相关性判据，再检索全库。已有完整检索可沿用其覆盖去向，按新的问题展开关联记录；不能只挑熟悉的游戏或支持推荐的例子。
- 全面检索不等于宽泛呈现。每个展开条目须说明它如何直接改变当前待决问题的答案；仅共享“死亡／失败／空间”等词，或只是其他系统会影响本题，不足以纳入本轮详细比较。跨题材料只登记去向，进入所属议题再展开；加上归属标签不能抵消跑题。若所谓待决点只是已定规则自然允许的结果，应撤回伪选择，不要求用户再次批准。此规则来自用户对 G01-Q03 范围过宽的纠正，不取消相关机制完整展开及稳定编号要求。
- 以机制为条目，不以游戏数量或预设方案数量为配额。不同的触发、作用对象、空间关系、时点、控制权限或主要成本，若会改变玩家判断，就分开列出；只是数值、外观或同构实现的区别可合并，但保留来源差异。
- 每条讲明原作具体过程：玩家先做什么、战斗自动发生什么、谁获益和付出什么、成立条件、反制／失败、版本与证据限制。规则事实、玩家实践、Agent 推论分别标明，不能靠游戏名和一句抽象标签代替内容。
- 相关但未推荐、互相冲突、需要不同操作权限／模式、历史失效、只有低置信线索的做法仍可见，注明类别与缺口。不能因当前不能直接移植就从比较中消失；也不能把线索补成已证实机制。
- 先展示独立机制及可组合、相冲突、依赖其他决定的关系，最后才综合推荐；不把能共存的机制包装成互斥套餐，不要求用户每轮必须选一个字母或整套方案。用户可逐条保留、追问、组合、否定或暂缓。
- 关键机制与有实质影响的差异要在对话中呈现，文档保存更完整的来源链；不能只在文件里堆材料，聊天仍只给结论。内容多时按因果环节分组供阅读，分组不表示省略组内不同机制。
- 对话和文档中的机制条目必须带一致、稳定的标识，方便用户直接引用。G01-Q02 已使用 K01–K78 表示机制比较项、L01–L12 表示待补证据线索；当前议题内可用短编号，跨议题引用时带上议题／子问题。新增条目追加编号，重新分组或排序不重编号，移除条目保留去向且不复用旧编号。
- 用户要求给既有内容加编号时，在完整原内容中加入编号，保留案例、差异、得失和限制；不能只另发删减细节的编号索引，让用户在两份回复间对照。后续机制讨论默认将编号与完整说明放在同一份可独立阅读的回复中。
- 全面展示不等于把每种机制都提交为全局规则选择。先说明基础规则、具体技能／装备／遗物特例、自然形成的战术及模式／权限差异各自归属；已确认的基础不反复表决，内容素材留待相应议题设计，不把整份清单变成逐项审批任务。G01-D03 是这一分工的首个明确决定。
- 2026-09-07 用户在 M03-Q03 再次明确：不同羁绊可以有不同影响体系，这类比较是具体内容的设计空间，不要求选择一种通用方式。认可各方式有合理性不等于全部进入初期，也不等于批准 Agent 对个别方式的优先级排序；保留完整编号材料，待设计具体内容时引用。
- 明示现有语料的覆盖与未完成部分，不宣称穷尽所有游戏机制；检索命中数、档案数、列项数均不代表质量或完备性。用户选择体验与玩法，Agent 负责研究解释和后续获授权的可行性核查。

## evidence.md

2026-09-07 用户在 M04-Q01 再次明确：不同效果应有不同持续状态结算方式。后续先判断材料是否属于具体内容的设计自由；这类材料保留完整比较和编号，但不反复提交为全局规则选择，也不因已有提案附带细化就将其全部记为用户决定。

记录本轮要回答的模型/机制问题，以及实际搜索范围：
- 检索词与同义表达、索引和正文路径、证据 id（存在时）、检索日期。
- 每种做法的来源、原作规则、玩家操作、实际得失、反例、版本与证据限制。
- 可迁移部分和不兼容前提必须与原作事实分开。
- 保留相关命中清单；合并展示同构机制，不遗漏差异或负面结果。
- 未读正文、证据不足、未覆盖和排除原因分别注明。只有商店页/摘要的线索不能冒充机制证据。
- 一开始就检索整个相关语料，不仅熟悉的游戏；首批命中后用关联机制扩展查询，不能声称绝对无遗漏。
- 未进行检索就明确写“未检索”，不要自动填研究结论。

## proposals.md

先列已定约束和本次待决子问题，再列可选方案、玩家体验后果、代价、前置依赖、反例和推荐。方案针对基础模型或通用机制；具体英雄/羁绊仅作说明，不能偷换议题。不存在已定的前置答案时说明假设，不替用户补决定。

## decisions.md

- 结论条目标识使用本议题 id 加序号，例如 G01-D01。
- 每条记录用户确认日期/本轮具体表述摘要、决定、理由、适用范围和未定细节。能取得来源任务/消息引用时附上，不能编造。
- 当前结论与被替代结论分开；调整时保留旧结论和替代原因，不删除有意义的决策历史。
- 仅确认研究/讨论流程不等于批准某个玩法方案。
- 记录受影响议题与对应 issue；状态与实施进度不混写。
- 已定当前规则只引用权威，除非本轮正在提议变更；新方向标注“已确认但未合并”。

## 原型与检验

先用静态例子或图示说明关系。代码、游戏资源、交互原型和试玩须遵循具体授权；不得因为有 artifacts 目录就默认制作。检验材料只证明实际覆盖，不把少数可行样例当成全体系平衡结论。
