# 游戏设计讨论区

本目录承载本轮长期玩法讨论。**不是现行玩法或实现权威。** 用户已确认按“全局边界 → 基础模型 → 整局机制 → 小批内容检验 → 最终整合”组织；阶段可按依赖回看，不是一次定死的流水线。

## 每次恢复先读

1. [讨论总览](roadmap.md)：当前议题、状态、下一步和依赖。
2. 当前议题的 README，以及已存在的 decisions.md：问题边界和最新用户决定。
3. [跨议题问题](05-integration/cross-topic-issues.md)：先检查会影响本题的未决依赖。
4. 有需要再读相关 evidence.md / proposals.md 和正式权威；不从记忆或旧方案标题推定结论。

专题检索已从 G01 战场体验开始；当前子问题、进度与下一步统一见 [讨论总览](roadmap.md)。检索整理、Agent 推荐与用户玩法决定分别记录，不能相互替代。

## 向用户呈现调研的方式

2026-09-06 用户要求：不要把大量调研过早压成 ABC 粗粒度选择；“只要是不同的机制，且与当前讨论点相关的，就应该列出来，我来思考决定”。因此先呈现相关机制清单、具体游戏做法及差异，再综合取舍和推荐。列入与否依据相关性及机制差异，不能依据 Agent 偏好；已选主轴也不能成为隐藏其他相关做法的理由。具体拆分、证据与呈现要求见 [记录约定](topic-records.md)。

## 权威与授权

- 现行 [玩法](../gameplay-design/README.md) 和 [系统契约](../system-design/README.md) 是当前实现依据，保留本轮开始前的有效内容；不因本轮建立讨论区而回退上一轮已完成的对齐。
- 从本轮开始，讨论结论只进入本目录。议题“已确认但未合并”不等于生效、已实现或已验收。局部决定后不逐题回写权威。
- 讨论完成后统一形成差异、检查模型间一致性，用户确认重要冲突与合并范围后再合入权威。未来如用户明确授权提前合并，必须单独记录范围，不默认扩大。
- 设计确认不是代码/资源/原型开发、发布或自动试玩授权。代码现状可核查，但不能用技术已有能力倒推产品已定。
- 调研库是只读证据，引用原路径和证据 id，不复制/改写原资产。Web 模型与浏览器草案也不自动同步。
- 阶段目录代表问题归属；同一个问题只维护一个当前结论。跨阶段修改用引用和影响记录，不再造第二份方案。

## 议题内的固定产出

- README.md：边界、前提、依赖、退出条件与阅读入口；不重复维护状态或详细决定。
- evidence.md：实际检索范围、检索词、命中文档/证据、机制差异、失败案例、版本限制和缺口。相似做法合并展示，但保留不同来源与差异。
- proposals.md：基于证据提出适合本项目的方案，注明取舍、依赖与 Agent 推荐；不把推荐写成用户决定。
- decisions.md：当前用户结论、理由、待定参数、适用范围与变更记录；是本议题讨论结果的唯一记录。
- artifacts/：确需图示、配置样例或已授权原型时创建。样例不自动成为正式内容。

目前只创建有实际边界信息的 README；其余按需创建。格式见 [议题记录约定](topic-records.md)。不按聊天轮次建文件，不堆 v1/v2/最终版。

## 收尾检查

每轮结束前：
- 有新证据则补检索记录，标明搜了什么、没能覆盖什么；不把关键词命中数量当完成率。
- 有用户决定才更新 decisions.md；只对本轮明确范围生效，保留先前决定的变更原因。
- 更新 roadmap.md 的当前议题、状态、完成到哪里和下一步；没有决定也如实记录。
- 发现跨议题影响就登记 issues，不能等最后靠回忆补，也不能擅自解决产品冲突。
- 不修改现行权威或调研库。最终合并另走 [整合流程](05-integration/README.md)。

## 排除项与定位

原 18 项是讨论来源，不是议题目录，也不是全部必做。常规融合、全员进化、科技树、全员职责指定和背包拼图不进入默认队列；历史构筑 Boss 保留意见。低频蒸馏及特定融合/进化可在 M06 和后续样例中检验规则边界，不另建通用系统。核心/功能位分工、效果联动等已确认原则作为约束，不反复表决。
