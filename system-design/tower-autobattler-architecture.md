# Tower Autobattler Architecture

Status: Accepted

## Responsibility

This document owns the project layers, scene/resource contracts, runtime-state boundaries, donor-asset boundary, and acceptance architecture for the complete Alpha.

## Layer Ownership

```text
Content scenes and read-only definitions
        ↓
Run application state and commands
        ↓
Deterministic battle simulation
        ↓ semantic battle events
Presentation, animation, audio, and UI
```

- Content owns authored identity and configuration, never mutable run truth.
- Run application owns the ordered persistent hero roster, population, formation/reserve state, hero equipment, run relics, tactical-command loadout, currency, route, rewards, unlock handoff, and save snapshot.
- Battle simulation owns combat legality, targeting, movement, timing, damage, effects, death, objectives, and outcome.
- Presentation consumes runtime facts and must not invent damage, victory, rewards, or progression.
- UI submits typed commands and renders view models; it does not mutate simulation collections directly.

## Content Platform Target

```text
Authored scenes/resources → validated compiled specs → scope-owned runtime instances
                                   ↓
                 deterministic requests/effects/events/triggers
                                   ↓
                immutable Battle → Run → Meta transitions
                                   ↓
                        versioned stable-id DTOs
```

- Ability, status/modifier, trait, equipment, relic, tactical-command, floor-rule, encounter/Boss, and reward systems retain separate ownership and lifecycles. They reuse typed source, magnitude, trigger, condition, target-query, attribute-modifier, effect, event, limit, and presentation primitives; they are not collapsed into one universal product type.
- Authored `.tscn` content roots and immutable `.tres` definitions compile into validated immutable runtime specifications before publication. Mutable health, mana, tactical points, cooldowns, modifiers, status stacks/durations, trait tiers, equipment projections, charges, counters, rolls, subscriptions, and queue state belong only to one explicit Battle, Run, or Meta scope owner.
- Resolution is ordered and non-reentrant: pre-resolution modifiers produce an authoritative effect result, the result publishes an immutable domain event, and reactive listeners enqueue later invocations. Every chain carries stable source/owner attribution, sequence and depth, bounded work, and an explainable terminal result.
- Content publication is transactional. Stable-id collisions, missing or mismatched references, dependency cycles, incompatible bindings, invalid scene contracts, and incomplete catalog-to-disk coverage reject the complete publication; sample content totals never define registry validity.
- The application composition boundary publishes one versioned `CompiledGamePackage`: the strict Catalog gate plus canonical Ability/Status/Trait/Equipment/Relic/TacticalCommand graph and the `GameProject` graph compile before any Registry, Project, graph, or version becomes visible. Boss phases participate in the same loadout reachability graph. Runtime consumers resolve canonical compiled products from that package instead of recompiling authored Resources.
- Scope activation and deactivation are symmetrical and idempotent. Success, defeat, timeout, abort, replacement, exception, and disposal remove subscriptions, pending invocations, and mutable instances owned by that scope.
- Cross-scope writes are forbidden. Battle produces a validated immutable transition result, Run applies it exactly once, and Meta changes only through its own use cases. Persistence serializes versioned DTOs with stable ids and mutable values, never live Nodes, compiled instances, or shared Resources.
- `GameProjectDefinition` is the authored project composition root; `CampaignDefinition` and `RunRulesDefinition` own campaign/run configuration. `RunApplication` remains the use-case facade over cohesive services. `GameRoot` is bootstrap only: it publishes the package, constructs the Run facade, and starts the authored screen host. `GameFlowCoordinator` owns routing plus exactly-once user-flow coordination, while `RunApplication` and `RunNodeResolutionService` own the settlement transaction; screen controllers bind view models and emit typed intent.
- Recombining existing primitives is scene/resource authoring only. A new atomic mechanic has one narrow typed processor/validator/description-test route. Concrete-id dispatch, reflection/string action languages, unrestricted global discovery, and mutable shared definitions are forbidden.

One `BattleEffectScope` owns the deterministic invocation queue, reactive subscriptions, per-binding limits, causal trace, and immutable transition result for each battle. Authored bindings compile before use; each resolution wave reads one immutable snapshot, prepares typed modifier requests, commits in stable order, then enqueues reactions from immutable resolved events. `BattleSimulation` remains the mutation authority for attacks, movement, damage/healing/shield, lethal resolution, and outcome while a Battle-local pure C# combat pipeline publishes their immutable typed phases. Migration adapters may temporarily leave an unmigrated production path direct, but they are compatibility boundaries rather than new authority and must migrate with their complete ordering contract.

## Independent Content Scene Contract

Every concrete roster hero, enemy, temporary-unit template, equipment/relic item, and tactical command is a separate `PackedScene` under a focused content directory. Each scene must instantiate successfully in a minimal preview/test host without a battle level, tower screen, HUD, or autoload-specific parent. Legacy soldier-tagged content is migration input to the roster-hero contract, not authority for a second persistent player-unit category.

### Unit Scene

Each unit scene has one unit root plus instanced component scenes, for example:

```text
UnitRoot
├── VisualRoot
│   └── AnimatedSprite2D
├── HealthComponent
├── CombatStatsComponent
├── TargetingComponent
├── MovementComponent
├── AttackComponent
├── AbilityComponent (optional)
└── UnitAnimationComponent
```

- A read-only `UnitDefinition` resource stores stable id, Chinese display name, tags, base stats, icon/visual references, and designer-facing descriptions. Scene ownership belongs only to its catalog entry.
- Runtime HP, cooldowns, targets, status effects, and position live on the instantiated nodes or battle state, never in the shared definition.
- Hero-specific behavior is supplied by focused components or abilities in the hero scene. Do not add a central switch over hero ids.
- A roster hero may reference immutable Ability and Trait contributions, but it neither owns the run's tactical-command slots nor supplies tactical points merely because it was the starting choice.
- Hero base combat attributes compile into an immutable attribute specification. Each Battle instantiation creates an independent mutable `BattleAttributeSet`; current health, current mana, shield, cooldowns, targeting, and position remain scope-owned runtime facts.
- The common root API is narrow: bind runtime identity, expose definition and team, accept simulation/presentation events, and emit typed lifecycle signals.

### Item Scene

Each equipment or relic item is an independent scene with an `ItemContentRoot` referencing the immutable product definition selected by its explicit classification. A read-only `ItemDefinition` resource stores identity, presentation, rarity, tags, and price; Equipment definitions project owner-scoped contributions, while Relic definitions compose Run-level Battle modifiers, reactions, counters, and outcomes. Scene ownership belongs only to its catalog entry.

- Items used only as run modifiers still remain scenes so they can be opened, composed, and tested independently.
- Relic item activation receives the matching canonical published Relic definition through its Run-owned sink. Equipment equip/replace commands resolve the matching canonical Equipment definition through the Run-owned equipment service. Neither path recompiles authored Resources or finds the battle or run by absolute node path.
- No central item-id switch is authoritative. Adding an item means authoring a scene, definition, and catalog entry.
- Equipment ownership is one concrete persistent hero instance with an authored slot capacity; the first production contract uses three slots. Mutable ownership, stacks, charges, counters, and per-run rolls belong to run state, not shared scene definitions.
- Existing production item classification and values remain unchanged until focused content authority reclassifies them; this migration adds only the required production-safe Equipment vertical slice by contract.

### Tactical Command Scene

- Each tactical command is independent authored content backed by one canonical compiled command/Ability definition; it is never a required child of a hero scene.
- Run state owns exactly two equipped command stable ids. Battle state owns exactly three shared tactical points, command cooldowns, and use counts; tactical points reset full for the next battle and are not persisted between floors.
- Activation preflights the authored one-to-three-point cost, optional currency cost, cooldown, use limit, target, landing capacity, and complete effect plan before commit. Failure leaves every resource and mutation unchanged.

### Components

- Reusable behaviors are separate component scenes with one responsibility.
- Children signal upward; composition roots call methods downward; unrelated systems communicate through typed application events.
- Components do not use parent-chain traversal or hidden sibling names. Required collaborators are explicit exported references or parent wiring.
- Content scenes may vary components without subclass explosions.

## Catalogs And Loading

- Stable ids exist only on definitions. A catalog entry owns exactly one `PackedScene` plus the same definition resource referenced by that scene root; it does not repeat the id or store a scene path in the definition.
- An id-to-entry registry is allowed for lookup. Concrete-id behavior dispatch is forbidden.
- Stable ids are ASCII and are the save-game and cross-reference keys.
- Human-facing scene/resource filenames and display names use Chinese where practical.
- Missing ids, scenes, definitions, or required components fail visibly with low-noise diagnostics. There is no silent placeholder for core content.
- Content discovery and validation happen before a run begins; combat hot paths do not scan directories.
- Catalog validation is bidirectional: every catalog entry must match one concrete content scene on disk and every concrete content scene must appear exactly once. Ids, scene references, and definition references are unique.
- Unit and item content roots expose authoring validation plus explicit bind/activate/deactivate lifecycles. A bare host can add any concrete scene to the tree and process a frame safely without a game root.
- Registry creation owns one scoped engine logger across the entire pipeline: it installs before catalog/structural validation performs its first scene instantiation, remains active through the batched hidden-host ready/process pass and all cleanup, and is removed only after captured errors are merged. First-pass structural instantiate/free plus ready-pass instantiate, attach, ready, process, detach, exit, and free errors all reject Registry publication, including errors that report without throwing or occur only once.
- Activation receives an explicit binding context for the Battle-local typed event pipeline, seeded randomness, command submission, and modifier registration. Content must not discover `/root`, `CurrentScene`, groups, parent chains, or cross-root `NodePath`s.
- Equipment and Relic effects register and unregister symmetrically. Mutable ownership, stacks, charges, counters, and rolls live in explicit Run/Battle instance state, never item, Equipment, or Relic definitions.
- Activation publication is transactional: failure restores the bound state. Deactivation clears local state before notifying collaborators, so cleanup remains stable even when an external sink fails.
- Validation returns a structured report. Any core error rejects run creation and makes headless validation exit non-zero; logging alone is not a gate.
- Cross-product authored publication validates catalog entries, independent floor-rule scenes, the complete Ability/Status/Trait/Equipment/Relic/TacticalCommand graph, and `GameProject` campaign/pool/encounter/Boss-timeline graph as one package. Any failure publishes neither a Registry, Project, compiled graph, nor non-zero publication version, and diagnostics retain the authored resource path plus binding/operation index. The production package entry point still runs the stricter bidirectional on-disk catalog gate.

## Mature Combat Build Contracts

- `BattleAttributeSet` evaluates one attribute as ordered base plus additive contributions, then multiplicative factors, then one deterministic override winner, followed by the attribute-specific clamp. Every contribution carries a stable `CombatSourceRef`, source-instance identity, and application order; authoritative removal by handle/source restores the exact remaining projection. Typed magnitudes cover constants, source/target attributes, invocation context, named team counts, and trait values with explicit snapshot-versus-live capture.
- Status/Modifier definitions own instant/timed/permanent duration, aggregation-by-source/target/independent policy, stack/overflow behavior, duration refresh, periodic reset, dispel category, death policy, granted state tags, sourced attribute modifiers, lifecycle/reactive bindings, and immutable presentation. Runtime identity includes definition, source, owner, application sequence, stacks, timing, and captured magnitudes; multi-source target aggregation is representable. Typed disposition is `Neutral`, `Helpful`, or `Harmful`; exact-id/source dispel remains available while owner-wide purge may filter by disposition and ordinary/strong strength, and `NonDispellable` always survives purge.
- Action authority queries typed state tags. For timed control using `LinearResistanceCeiling`, effective duration is `max(1, ceil(authored_ticks * (1 - clamp(ControlResistance, 0, 1))))`; removal, expiry, dispel, death, and scope teardown reverse all sourced contributions idempotently.
- Active Status combat reactions subscribe only to attack declared/landed, Ability resolved, damage/healing/shield resolved, or unit defeated/killed facts. `OwnerIsSource` matches the event source and freezes the event target as the explicit counterpart; `OwnerIsTarget` matches the event target and freezes the event source as the explicit counterpart. The immutable invocation also preserves the complete typed event and uses its `EffectiveValue` as invocation magnitude. A target-aggregated multi-source Status owns one subscription per compiled binding, attributes execution to its deterministic `PrimaryContribution`, and transfers that attribution without replacing the subscription when the primary source is removed. Listeners enqueue through the Battle reaction sink and never execute gameplay synchronously inside event publication.
- Scope completion removes modifiers and subscriptions before callbacks, emits immutable `ScopeCompleted` Removed lifecycle facts and presentation cues, but deliberately suppresses gameplay Removed bindings because the Effect scope is already terminal. Cleanup or callback failures leave every Status removed and every subscription detached, then publish an `Exception` Status transition; normal completion retains its requested reason.
- `TraitDefinition` owns typed contributions/counting policy and ordered breakpoint ranges with compiled effect loadouts. One team-level Battle trait scope derives a contribution snapshot, removes the old tier source, and applies exactly one new tier source through shared primitives. Temporary-unit counting, duplicate identity, deployment-only counting, and extra contributions are data policies; trait value `30` never implies thirty bodies.
- Equipment projects only from its concrete persistent hero owner and may contribute attributes, Abilities, Statuses, reactive bindings, or Traits. A reactive Equipment binding compiles one supported typed combat event, owner/event-target selection, Equipment-instance source attribution, priority, and one canonical Status reference. Equipment→Status dependencies plus every binding field participate in authored, compiled-definition, and package fingerprints; a missing dependency rejects the complete package atomically. Because an Equipment instance has no `BattleAttributeSet`, an Equipment-instance sourced binding whose direct or overflow-reachable Status modifier reads a source Attribute is publication-incompatible and rejects the complete compiled definition; the same graph remains valid with Owner source attribution.
- One Equipment instance owns at most one combat subscription for each required event kind. When an immutable event matches that concrete owner, all matching bindings are ordered and submitted once as one Status-application batch. Before that deferred reaction commits, every resolved application target must still satisfy the Battle's generic Status-target eligibility query; a lethal `AttackLanded` fact remains published and may advance a surviving owner's Status, but cannot recreate Status state or cues on its defeated event target after death cleanup. `BattleStatusScope` remains the sole owner of batch preflight, stack/duration/threshold mutation, source attribution, transition, and rollback; Equipment neither owns Status state nor partially commits one event's declarations. Victory, defeat, timeout, abort, replacement, exception, and disposal clear every Equipment subscription, instance, and modifier handle idempotently.
- Relics remain Run-level and may project static sources or subscribe to only the typed Battle events they require. Reactive Relic counters declare Battle/Run ownership, threshold, consumption, and reset; duplicate instances remain source-isolated. Relic Attribute and Battle-start declarations also compile explicit stack/repeat policies: ordinary `PerStack` declarations retain independent sourced contributions, while empty-slot `LinearAcrossStacksAndInstances` declarations aggregate by Relic stable id plus binding id, sum all matching instance stacks, and project one handle per target from the first registered instance in stable Battle order. Its additive magnitude is `base × empty slots × total stacks`; its multiplicative magnitude is `1 + empty slots × (base - 1) × total stacks`. `OncePerBattleBinding` uses the same definition/binding key and attributes its single execution to that first instance. These policy fields participate in authored, compiled-definition, and package fingerprints.
- One production Frost/Freeze slice must connect hero-owned equipment attack-speed growth, attack-landed Frost application with source attribution, an authored Frost threshold, timed action-disabling Freeze with control resistance, one ordinary Trait breakpoint, immutable presentation cues, deterministic ordering, and complete rollback without concrete-id dispatch.

## Battle Runtime

- Combat advances on a stable simulation cadence independent from animation frame rate.
- Units use a small explicit state model such as deploying, seeking, moving, attacking, casting, recovering, disabled, and defeated.
- Targeting, movement, attacks, Abilities, Statuses, Traits, Equipment, Relics, tactical commands, floor rules, and unit rules communicate through typed commands/events and focused services.
- Simulation resolves truth before presentation plays the corresponding cue.
- Player formation sources apply only to their authored team/owner. Unit-authored adjacent auras and team Trait sources remain local to the owning team.
- A seeded random source is owned by the run/battle session so saves and tests can reproduce content choices and combat setup.
- The first implementation may use grid steering instead of general-purpose navigation, but navigation ownership must remain replaceable behind a movement service.
- The deterministic grid-movement service separates stable strategic targets from engagement goals. At tick start it captures one living occupancy/terrain snapshot; every queued request completes ordered target/goal/next-step candidate generation from that snapshot before any reservation mutation. One central deterministic, battle-seeded and team-neutral arbitration then jointly assigns unique scarce goals and next cells, retries each request's next-best candidate after goal, destination, or dependency rejection, and commits the dependency-safe moves together. Actual path cost to a legal attack/heal position is the primary spatial cost, with authored role preference and target hysteresis secondary.
- Engagement goals are exclusive final ownership but are not global terrain walls. Current enemy cells remain impassable; friendly cells may be entered only through an accepted same-resolution follow chain. Same-cell commits, direct swaps, and dependency cycles are rejected. Blocked plans retain bounded leases before replan/retarget, and staging is allowed only when it improves distance or line access. Waiting age records real obstruction and resets after progress or completed action.
- `BattleSimulation` remains authoritative for immediate-action precedence, healing range/line access, cooldowns, damage, and death. Healers fall back to ordinary combat when no legal wounded-ally plan exists. Authoritative death is terminal without an explicit resurrection mechanic: ordinary healing, lifesteal, and subsequent status resolution cannot raise a defeated unit's health. Death releases the dead unit plus all dependent targets, goals, reservations, and queued intents in the same tick; next-tick, battle replacement, and disposal perform defensive stale-state cleanup.
- Tactical-command activation is a simulation transaction. Legality, shared tactical points, optional gold, cooldown, use limit, target/effect plan, and summon capacity are validated before commit; failed activation publishes a typed reason and leaves all command resources and runtime state unchanged. Tactical points are Battle-local mutable state and never enter the run save DTO.
- The Battle-local combat pipeline publishes immutable typed facts for battle start/completion, attack declared/landed, Ability resolution, damage/healing/shield resolution, Status application/stack/removal, summon/move, defeat, and kill. Pre-resolution calculation accepts typed modifier requests; post-resolution listeners may only enqueue later bounded work and cannot synchronously re-enter the mutation in progress.
- The combat pipeline is pure C# infrastructure owned and disposed by one Battle. Victory, defeat, timeout, abort, replacement, exception, and disposal clear every subscription, pending invocation, Attribute/Status/Trait/Equipment/Relic projection, and presentation-cue lifecycle idempotently; it is never a global Autoload EventBus.
- Unit presentation owns animation lifecycle only. Each event batch is reduced per unit by `defeated > skill_cast/attack > hit > move/idle`; one bounded pending action prevents lower-priority cues from erasing attacks without creating an unbounded backlog. Attack, hit, and skill-cast cues are protected one-shots. Every authored frame is shown by fitting the full clip into a configurable action window rather than truncating its tail; defeat holds only after its full clip, then fades/hides idempotently. Presentation routes source cues and target cues explicitly and cannot recreate or re-defeat a hidden unit during synchronization.
- Spatial motion is a separate reusable presentation component with an explicitly bound unit-root target. `BattleSimulation` and `DeterministicGridMovementService` remain the sole owners of authoritative cells, legality, reservations, timing, move-event order, and digest; the motion component never writes simulation state or chooses a destination.
- `BattleScreenController` routes every accepted `move` event and its event `Cell` to the matching motion component in event order before per-unit cue arbitration. Cue priority may suppress a move animation cue for an action, but it cannot discard the spatial waypoint. Ordinary presenter synchronization refreshes health and animation facts without writing transforms.
- `BattleScreenController` also consumes immutable damage/healing facts and Status presentation cues by append-only cursors. One independently authored non-interactive board overlay instances one authored floating-label scene; typed fact kind or Status lifecycle alone selects concise Chinese/sign text, RealmTheme variation, and draw layer. Same-tick target/Status duplicates are coalesced, active nodes are capped at `64`, and each node kills its prior Tween before playback. Battle replacement, terminal presentation, controller teardown, and tree exit detach every cue and kill every owned Tween; selected-unit exact Status stacks/duration remain a separate immutable detail surface.
- Initial presenters, summons, bind/reset, and explicit battle replacement use a snap API once. Normal movement uses a persistent process-driven interpolator with an editor-authored bounded waypoint queue, initial 1x/2x/4x segment durations of approximately `0.24 / 0.14 / 0.09` seconds, and an approximately 0.25-second maximum visual-lag budget in effective presentation time at supported frame cadence. Spatial progress applies one bounded monotonic ease-in/ease-out profile only along the current source-to-destination segment; it cannot overshoot, reverse, round a corner, skip an ordered cell center, or alter authoritative timing. Parent battle processing may enqueue events before child motion processing in the same frame, so fresh work defers pre-event frame delta. Per-frame delta and carried credit are bounded, at most one ordered segment completes per rendered frame, and completion/defeat/reset/teardown discard old credit. This preserves a visible sample after a hitch; it does not create competing transform Tweens or an unbounded callback backlog.
- `UnitContentRoot` explicitly coordinates motion and animation presentation. Motion publishes state, horizontal-segment, and normalized segment-progress facts upward; the composition root routes them downward to `UnitAnimationComponent`. The animation component owns only its character sprite's decorative step offset and bounded move phase, never the unit-root transform or readability children. The initial step lift target is approximately three pixels at mid-step and exactly zero at both endpoints. Snap, completion, defeat, bind, deactivate, reset, replacement, and tree exit clear that offset; pause freezes it with root progress. Components do not discover or call siblings through parent-tree traversal.
- The battle presenter propagates pause and speed changes to spatial motion and animation presentation. Pause freezes the current interpolation, character-only lift, and animation frame; resume continues from the same progress. Speed changes retime the active segment in place. Motion determines the `move`/`idle` base cue while action one-shots remain an independent priority layer. Re-entering the move base cue for consecutive segments retains or advances a bounded presentation-only phase when the resolved `SpriteFrames` animation supports it, avoiding an opening-pose restart without requiring a full clip at fast speed.
- Horizontal facing is presentation state and never enters the digest or action legality. `UnitAnimationComponent` owns the authored source-facing convention and mirrors only its `AnimatedSprite2D`; bind/reset supplies the team default. Motion updates facing when a real segment begins, while attack/heal presentation faces the event target from current visible positions. Vertical motion retains facing and defeat makes it terminal.
- The selected-unit panel renders the simulation's explicit action mode, target, and remaining cooldown as Chinese facts. It neither infers navigation decisions nor mutates simulation state.
- Defeat is terminal across both animation and motion presentation: it clears queued waypoints at the current visible position, restores the character-only decorative offset to zero, and then plays the defeat cue. Bind, deactivate, tree exit, presenter disposal, and battle replacement clear motion state, move phase, decorative offset, and processing so no stale waypoint or callback can slide, reveal, or recreate a unit. Pointer hit testing continues to use the visible presenter transform between cells.
- `BattleSimulation` owns per-runtime-id report statistics at the same mutation points that apply damage, shield loss, healing, attacks, terminal death, and summons. Effective damage is the capped health-plus-shield change, effective healing is the capped health restoration, damage dealt/taken mirror one authoritative fact, and kill credit requires the concrete source that caused the living-to-defeated transition. Initial units join at tick zero; a temporary summon captures the current join tick; the first terminal defeat writes its tick once. Attack actions increment once at the attack authority before splash/piercing targets, while a credited positive `HealLiving` result increments one effective healing event. Only a committed successful tactical command increments the battle-level use count. Floor/environment sources remain unowned and statistics never enter the digest or decision path.
- `BattleResult` is an immutable post-battle boundary made from value snapshots with stable runtime/content/source ids and numeric facts, including join/defeat ticks, action/event counters, and successful command uses. It never exposes live `BattleUnitState`, Nodes, textures, or mutable shared resources. `RunApplication` consumes the snapshot's stable source id and final-health facts without changing the save schema.
- `BattleScreenController` owns fixed-step coordination and maps displayed `x1`/`x2`/`x4` modes to real-time simulation scales `0.8`/`1.6`/`3.2` while presentation receives the displayed mode. On the terminal tick it stops stepping, captures one result, locks battle interaction, preserves the final board for the authored hold, and owns one real-time fade Tween. Replacement, a new battle, or tree exit kills and resets that Tween; confirm may fast-forward the hold/fade but cannot bypass the report.
- `GameFlowCoordinator` retains the terminal `BattleResult` and encounter, asks `RunApplication` for a typed `RunBattleResolution`, and creates a post-report route only when that resolution is accepted. Accepted defeat/timeout is a committed failure outcome; a rejected or persistence-failed victory is not defeat, does not lock the flow, and keeps the same immutable settlement inputs available for one explicit player retry at a time. The authored report scene exposes concise visible retry feedback and re-enables its existing continue action as `重试结算`; it never auto-loops. A successful retry commits exactly once and follows the normal reward/success route. Repeated frames, terminal callbacks, teardown, and already-accepted requests are idempotent. `RunNodeResolutionService` remains the sole owner of settlement authentication, working-copy mutation, persistence publication, and transition identity.

## Tower And Floor Rules

- Tower regions, nodes, encounters, reward tables, and floor rules are authored resources or scenes and loaded through catalogs.
- Each floor-rule scene implements one lifecycle contract: validate setup, apply battle modifiers, react to fixed simulation ticks/events, expose readable preview text, and clean up.
- A started or partially started floor rule receives exactly one end callback on normal resolution, explicit battle replacement, scene teardown, or simulation failure. Battle simulation abort/dispose is idempotent.
- Encounters reference floor-rule scenes; the battle root does not switch on floor ids.

## UI And Composition Roots

- Main menu, hero selection, tower route, roster/deployment, battle HUD, reward/shop/event/rest, pause/settings, and result screens are authored scenes.
- Repeated cards, rows, slots, tooltips, and unit/item previews are reusable child scenes.
- Composition roots bind view models and route typed commands. They do not construct full control trees in C#.
- Reusable presentation components own named visual states for default, hover/focus, selected, drag source, legal/illegal destination, swap/occupied target, disabled, transient success, and transient failure as applicable. Controllers bind semantic state and concise accessibility/detail text; Theme resources and authored scenes own shape, color, icons, and motion. Presentation state never decides gameplay legality or persistence.
- Dynamic list owners reconcile authored child instances by stable identity. A state-only refresh rebinds and reorders existing controls; composition changes add missing children and remove stale children only outside the input event-source lifetime, with C# signal connections disconnected symmetrically. A callback may not synchronously free the Control that is emitting its input event or any ancestor that owns that dispatch.
- Interaction acceptance drives real viewport input through Control hit testing, focus, and drag/drop for representative mouse and keyboard/gamepad paths. Direct signal emission remains valid for isolated typed-command tests but is never evidence that the player-facing control is operable.
- The desktop design viewport and default normal window are both `1600×900`; startup is explicitly windowed, resizable, non-fullscreen, and non-maximized. Godot `canvas_items` plus `expand` remains the stretch contract, and authored containers, anchors, size flags, and local scroll ownership keep `1280×720` usable without a second fixed layout.
- `UnitPortraitDefinition` is read-only presentation data owned one-per-concrete-unit and references existing local `SpriteFrames` plus an authored animation/frame, zoom, normalized offset, and optional horizontal flip. It does not own crop dimensions: each consumer-authored square `UnitPortrait` control supplies the visible clipping rect and display size. Catalog/presentation validation derives portrait completeness from the unit catalog and requires one unique, valid portrait resource per concrete unit; missing, duplicate, mismatched, or uncataloged production data fails before publication.
- `UnitPortrait` is an authored reusable presentation scene. Each instance owns an independent UI `AnimatedSprite2D` bound to the definition's existing `SpriteFrames` and animation, starts from the authored frame, preserves zoom/offset/flip, plays at a calm UI speed, and pauses while not visible in the scene tree. It owns no stable-id lookup, selection, gameplay facts, mutable run state, battlefield sprite, battle animation state, shared-resource mutation, or content-id branching. Hero selection, recruitment, deployment lists, Army details, and battle-report rows bind the same definition through their existing view models and author only context-specific display size.
- A `UnitPortrait` consumer may author a horizontal context mirror that defaults off. Both the animated-sprite leaf and fallback-texture leaf use `UnitPortraitDefinition.FlipHorizontal XOR ContextMirrorHorizontal`; binding never mutates the shared definition. Only the `EnemyDeploymentPreview` portrait instance enables this deployment context, so its character art faces the player zone while the outer preview, badges, neutral consumers, and battle presentation remain unchanged.
- `UnitChoiceCard` is the authored focusable recruitment template. It owns separate portrait, name, restrained responsibility/faction badges, prominent health/damage/reach stat blocks, neutral description, and contextual-meta regions and emits one typed stable-id choice signal. Recruitment uses its compact baseline. The general `ChoiceCard` remains authoritative for tower routes, items, shops, and other non-unit choices.
- Hero selection is an authored responsive master-detail composition. `HeroLibraryTile` owns only identity and emits one typed selection request from button activation; mouse hover and focus never emit selection. `HeroDetailPanel` binds the explicitly selected hero, owns the single fixed primary action, and emits that stable id exactly once. The screen composition root authors one deterministic initial selection, instantiates only authored tile templates, changes grid density at the supported width boundary, and keeps hover/focus presentation separate from committed selection and run activation.
- `StatBlock`, `TraitBadge`, `ResourceCostBadge`, and `HeroAbilityPanel` are independently inspectable authored component scenes with typed binding APIs. Runtime code binds existing definition/command facts and may instantiate those templates; it must not build replacement trees, parse presentation prose, or dispatch on concrete hero ids.
- One read-only validated `SemanticIconCatalog` resource owns the mapping from stable presentation meanings to tintable source icons and optional Theme roles. `SemanticChip` is the authored icon-plus-Chinese-text component; fixed facts are authored scene instances and variable groups instantiate only that template. Controllers bind semantic keys and existing view-model values, while the catalog remains the sole icon resolver. Responsibility, faction, exact reach, stable combat facts, and tower-node type may be presentation categories; concrete content ids and per-screen path maps are forbidden.
- Hero selection, recruitment, deployment, Army details, battle reports, selected-unit facts, and tower-route choices reuse that catalog identity. Faction gameplay tags resolve to their matching faction semantic. Tower cards use their node-type icon as primary identity and bind risk as a separate semantic fact; the general choice-card size, focus, and typed selection contract remain unchanged.

## Persistence

- Save data is a versioned DTO written under `user://`; it contains stable ids and mutable values, not serialized live Nodes or shared Resources.
- Meta progress, settings, and an active run have separate ownership and validation.
- Loading validates schema version and referenced content before publishing state. Corrupt or incompatible active-run data fails safely without erasing valid meta progress.
- Schema version 3 remains a compatibility input for the former starting-hero plus six-entry soldier formation. The next active-run schema owns one ordered persistent hero roster with stable per-instance identity, current/effective population sources, per-hero equipment instance slots, exact formation cells, two equipped tactical-command stable ids, and Run-level Relic instance state.
- Migration advances incrementally from v3 only when every legacy player identity, health fact, formation cell, item/relic fact, command choice, and deployable population capability can be represented losslessly. v2/v3 migration derives current population as at least the authored compatibility initial population or the migrated roster count when higher, but never above the ordinary cap `10`; an over-cap legacy roster is rejected instead of truncated. An ambiguous or lossy active Run is rejected explicitly without erasing valid Meta or Settings; migration never silently drops a roster member, item, equipment owner, cell, population capability, or mutable fact.
- Save and migration contracts use isolated test namespaces. Tests never load, migrate, overwrite, or delete the player's default active-run path.
