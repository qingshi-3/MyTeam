# Tower Autobattler Architecture

Status: Accepted

## Responsibility

This document owns the project layers, scene/resource contracts, runtime-state boundaries, donor-asset boundary, and acceptance architecture. Default Expedition and legacy Tower profile selection, action state, and save transactions are authoritative in [Run progression and sessions](run-progression-and-sessions.md).

## Layer Ownership

### Authored encounter progression (legacy Tower placement)

`EncounterDefinition` owns optional per-local-floor health/attack curves and complete `EncounterCompositionDefinition` formations. Compilation copies curves, eligible local-floor ranges, enemy ids and enemy-side anchors into immutable values; rejects missing floor coverage, invalid multipliers or anchors, unknown units and mismatched bosses. Empty curves/templates retain the legacy encounter path for existing fixtures; production encounters author both.

`TowerGenerator` selects an eligible template and floor rule solely from Run seed/floor and encounter salt. `EncounterPlan` carries its identity and anchors; the title includes the readable formation name. Templates replace random leader/filler generation rather than supplement it. `RunBattlePreparationService` multiplies regional and local curves into initial enemy snapshots; it never mutates unit Resources. `RunBattlePreparationAdapter` resolves terrain/body-safe enemy placement once for both preview and battle. Settlement regenerates the expected template and authenticates its identity, enemies and anchors alongside the existing encounter fields. That Tower encounter change did not require a new save version. Default Expedition now has its own typed progression, profile header and action state; see the session contract.

Numerical baselines live in encounter/trait Resources; calibration entry points and evidence live in `work-items/archive/enemy-difficulty-and-build-gates.md`. These preparation multipliers do not imply universal scaling of authored fixed-value effects or later summons.

```text
Content scenes and read-only definitions
        ↓
Run application state and commands
        ↓
Deterministic battle simulation
        ↓ semantic battle events
Presentation, animation, audio, and UI
```

- Content owns authored identity and configuration, never mutable run truth.
- Run application owns the ordered persistent hero roster, population, formation/reserve state, hero equipment, run relics, tactical-command loadout, currency, route, rewards, unlock handoff, and save snapshot.
- Battle simulation owns combat legality, targeting, movement, timing, damage, effects, death, objectives, and outcome.
- Presentation consumes runtime facts and must not invent damage, victory, rewards, or progression.
- Basic sound feedback is view-owned: authored `FeedbackAudio.tscn` instances provide bounded voices for the app UI and battle screen. `UiFeedbackBinding` covers existing and later-created buttons in its explicit root scope. `GameRoot` injects `MainMenu` as the only hover scope: enabled pointer entry or non-hovered focus entry sounds once there, with no extra press cue. Internal buttons stay silent on hover/focus and sound on accepted `Pressed` input, including keyboard/controller activation and actions that immediately hide their screen. Accepted/rejected command results outrank generic selection within the same input. Bindings detach on button exit and root disposal. `BattleAudioFeedback` consumes projectile, combat, status-lifecycle and presentation facts; content-specific ability cues are authored in the audio scene. No audio clock or pitch variation consumes simulation RNG. Pause/replacement/exit clear or pause owned voices, and Master settings remain the volume authority. Asset provenance and current mappings live in `assets/audio/README.md`.
- Concrete item illustrations belong to each `ItemDefinition.Icon`, independently of the semantic icon catalog. `assets/ui/items/` contains the generated sources and prompt manifest; the import limit and mipmaps support small inventory use without changing unit sprite filtering.
- Unit action audio is authored on `UnitAnimationComponent.FrameSounds` as independent `UnitAnimationSound` resources (logical action, one-based frame, `FeedbackSound`). Actual sprite progression requests playback through the active unit presenter and the view-owned mixer; timed projectile animation catches crossed frames once. Unstarted queued actions and canceled actions do not backfill sound. Configured actions suppress their legacy event action cue; actual impacts, effective healing/shield receipts and other outcome cues remain fact-driven. Battle Lab and campaign share this path. The Lab preview instantiates the same content scene with duplicated editable markers; audition never changes shared resources or simulation timing. Authoring instructions live in `content/audio/README.md`.
- UI submits typed commands and renders view models; it does not mutate simulation collections directly.
- Combat mixing uses immutable `FeedbackMixGroup` resources for cross-cue admission limits, alongside each sound's own limits. The view-owned mixer keeps group timestamps, per-voice elapsed time and a highlight ducking envelope; none is shared Resource state. Accepted highlights briefly attenuate duckable voices, including newly started ones, with smooth recovery. Optional duration caps fade tails. Pause freezes envelopes and tail clocks, clear resets them; rejected sounds are dropped without a delayed queue. Interface sounds have no combat group. Current tuning is documented in `content/audio/README.md`.

## Content Platform Target

```text
Authored scenes/resources → validated compiled specs → scope-owned runtime instances
                                   ↓
                 deterministic requests/effects/events/triggers
                                   ↓
                immutable Battle → Run → Meta transitions
                                   ↓
                        versioned stable-id DTOs
```

- Ability, status/modifier, trait, equipment, relic, tactical-command, floor-rule, encounter/Boss, and reward systems retain separate ownership and lifecycles. They reuse typed source, magnitude, trigger, condition, target-query, attribute-modifier, effect, event, limit, and presentation primitives; they are not collapsed into one universal product type.
- Authored `.tscn` content roots and immutable `.tres` definitions compile into validated immutable runtime specifications before publication. Mutable health, mana, tactical points, cooldowns, modifiers, status stacks/durations, trait tiers, equipment projections, charges, counters, rolls, subscriptions, and queue state belong only to one explicit Battle, Run, or Meta scope owner.
- Resolution is ordered and non-reentrant: pre-resolution modifiers produce an authoritative effect result, the result publishes an immutable domain event, and reactive listeners enqueue later invocations. Every chain carries stable source/owner attribution, sequence and depth, bounded work, and an explainable terminal result.
- Content publication is transactional. Stable-id collisions, missing or mismatched references, dependency cycles, incompatible bindings, invalid scene contracts, and incomplete catalog-to-disk coverage reject the complete publication; sample content totals never define registry validity.
- The application composition boundary publishes one versioned `CompiledGamePackage`: the strict Catalog gate plus canonical Ability/Status/Trait/Equipment/Relic/TacticalCommand graph and the `GameProject` graph compile before any Registry, Project, graph, or version becomes visible. Boss phases participate in the same loadout reachability graph. Runtime consumers resolve canonical compiled products from that package instead of recompiling authored Resources.
- Scope activation and deactivation are symmetrical and idempotent. Success, defeat, timeout, abort, replacement, exception, and disposal remove subscriptions, pending invocations, and mutable instances owned by that scope.
- Cross-scope writes are forbidden. Battle produces a validated immutable transition result, Run applies it exactly once, and Meta changes only through its own use cases. Persistence serializes versioned DTOs with stable ids and mutable values, never live Nodes, compiled instances, or shared Resources.
- `GameProjectDefinition` is the authored project composition root; `CampaignDefinition` and `RunRulesDefinition` own campaign/run configuration. `RunApplication` remains the use-case facade over cohesive services. `GameRoot` is bootstrap only: it publishes the package, constructs the Run facade, and starts the authored screen host. `GameFlowCoordinator` wires typed intents and routes screens; `RunBattleFlow` owns deployment and the campaign battle/report/retry lifecycle, while `BattleLabFlow` owns the editable laboratory session, frozen reset configuration and laboratory report return. These feature flows receive only their required screen controllers and navigation callbacks, not the whole screen host or coordinator. `RunApplication` and `RunNodeResolutionService` remain the settlement transaction authority; screen controllers bind view models and emit typed intent.
- Recombining existing primitives is scene/resource authoring only. A new atomic mechanic has one narrow typed processor/validator/description-test route. Concrete-id dispatch, reflection/string action languages, unrestricted global discovery, and mutable shared definitions are forbidden.

One `BattleEffectScope` owns the deterministic invocation queue, reactive subscriptions, per-binding limits, causal trace, and immutable transition result for each battle. Authored bindings compile before use; each resolution wave reads one immutable snapshot, prepares typed modifier requests, commits in stable order, then enqueues reactions from immutable resolved events. `BattleSimulation` remains the mutation authority for attacks, movement, damage/healing/shield, lethal resolution, and outcome while a Battle-local pure C# combat pipeline publishes their immutable typed phases. Migration adapters may temporarily leave an unmigrated production path direct, but they are compatibility boundaries rather than new authority and must migrate with their complete ordering contract.

The implemented module boundaries and migration constraints are specified in [战斗运行时职责拆分](battle-runtime-modules.md). `BattleAbilityExecutor` owns preparation and commit sequencing; `BattleAbilityEffectOperations` owns generic effect/status/cooldown operation rules; `BattleAbilitySummons` owns reservations, validation and deferred trait bonuses. `BattleStatistics` owns counters, report freezing and an opaque checkpoint. `BattleEnemyActionScope` owns targeting, cast phases, returning blades and brood/product lifetimes through read-only queries, typed commands and explicit transaction ports. These modules do not hold the simulation or mutable units. The simulation retains world transactions and integration adapters; remaining trait, lifecycle and other mechanism rules are still migration work, not implicitly independent modules.

## Independent Content Scene Contract

Every concrete roster hero, enemy, temporary-unit template, equipment/relic item, and tactical command is a separate `PackedScene` under a focused content directory. Each scene must instantiate successfully in a minimal preview/test host without a battle level, tower screen, HUD, or autoload-specific parent. Legacy soldier-tagged content is migration input to the roster-hero contract, not authority for a second persistent player-unit category.

### Unit Scene

Each unit scene has one unit root plus instanced component scenes, for example:

```text
UnitRoot
├── VisualRoot
│   └── AnimatedSprite2D
├── HealthComponent
├── CombatStatsComponent
├── TargetingComponent
├── MovementComponent
├── AttackComponent
├── AbilityComponent (optional)
└── UnitAnimationComponent
```

- A read-only `UnitDefinition` resource stores stable id, Chinese display name, tags, base stats, icon/visual references, and designer-facing descriptions. Scene ownership belongs only to its catalog entry.
- Runtime HP, cooldowns, targets, status effects, and position live on the instantiated nodes or battle state, never in the shared definition.
- Hero-specific behavior is supplied by focused components or abilities in the hero scene. Do not add a central switch over hero ids.
- A roster hero may reference immutable Ability and Trait contributions, but it neither owns the run's tactical-command slots nor supplies tactical points merely because it was the starting choice.
- Hero base combat attributes and circular body geometry compile into immutable specifications. Each Battle instantiation creates an independent mutable `BattleAttributeSet`; current health, current mana, shield, cooldowns, targeting, continuous logical position, velocity intent, and planning state remain scope-owned runtime facts.
- The common root API is narrow: bind runtime identity, expose definition and team, accept simulation/presentation events, and emit typed lifecycle signals.

### Item Scene

Each equipment or relic item is an independent scene with an `ItemContentRoot` referencing the immutable product definition selected by its explicit classification. A read-only `ItemDefinition` resource stores identity, presentation, rarity, tags, and price; Equipment definitions project owner-scoped contributions, while Relic definitions compose Run-level Battle modifiers, reactions, counters, and outcomes. Scene ownership belongs only to its catalog entry.

- Items used only as run modifiers still remain scenes so they can be opened, composed, and tested independently.
- Relic item activation receives the matching canonical published Relic definition through its Run-owned sink. Equipment equip/replace commands resolve the matching canonical Equipment definition through the Run-owned equipment service. Neither path recompiles authored Resources or finds the battle or run by absolute node path.
- No central item-id switch is authoritative. Adding an item means authoring a scene, definition, and catalog entry.
- Equipment ownership is one concrete persistent hero instance with an authored slot capacity; the first production contract uses three slots. Mutable ownership, stacks, charges, counters, and per-run rolls belong to run state, not shared scene definitions.
- Existing production item classification and values remain unchanged until focused content authority reclassifies them; this migration adds only the required production-safe Equipment vertical slice by contract.

### Tactical Command Scene

- Each tactical command is independent authored content backed by one canonical compiled command/Ability definition; it is never a required child of a hero scene.
- Run state owns exactly two equipped command stable ids. Battle state owns exactly three shared tactical points, command cooldowns, and use counts; tactical points reset full for the next battle and are not persisted between floors.
- Activation preflights the authored one-to-three-point cost, optional currency cost, cooldown, use limit, target, landing capacity, and complete effect plan before commit. Failure leaves every resource and mutation unchanged.

### Components

- Reusable behaviors are separate component scenes with one responsibility.
- Children signal upward; composition roots call methods downward; unrelated systems communicate through typed application events.
- Components do not use parent-chain traversal or hidden sibling names. Required collaborators are explicit exported references or parent wiring.
- Content scenes may vary components without subclass explosions.

## Shared Combat VFX

- Burn no longer includes fixed translucent flame-root sprites; its flowing particles use instance-local material time. Burn alone opts into a small upper-tip sway through `BurnFlameParticle.tscn`; this does not change particle placement, size or lifetime, or the shared jet material. `VfxJetTrack` uses the restored projected stream with cast-relative supply and real-time transit/shutoff, plus independent downstream flame/smoke/ember particles. The combined density-field experiment was rejected and removed. Animated ambient materials are instance-local; pending births are suppressed after cancellation.
- `VfxLightningTrack` owns a static branched strip mesh with connected branch roots and fixed endpoints; an instance-local shader samples conduction, core/corona and real-time decay. `VfxCrystalTrack` grows authored individual prism sprites from fixed bases, then fractures locally; crystal size is compensated independently of area scaling. Their action starts follow cast speed, tails use real local seconds, and cancellation suppresses pending layers. Ballistic particles optionally add lift and spin (zero by default); timed groups can opt into cast-relative delay without scaling child decay clocks.
- Battle presentation and the independent VFX preview consume the same `VfxCatalog`, immutable `VfxDefinition` resources and authored effect scenes. A stage supplies projection and scale; the preview does not instantiate a simulation or access saves.
- `VfxRiseTrack` samples a bounded impulse of upright authored plume sprites: cast-relative births, real-time acceleration/stretch/tails, local texture erosion and no pending births after cancellation. `VfxPoolBubbleTrack` owns independent surface positions and grow/pop/ripple phases with instance-local materials; unequal periods prevent whole-emitter restart, and release allows only already-started cycles to finish. Both receive playback parameters explicitly, compensate particle size for range scaling, freeze motion under reduced-motion settings and clean up with their owning instance. Dynamic children here are bounded particle instances, not an ad hoc content scene hierarchy.
- Each stage owns its `VfxPlayer`; every `VfxInstance` owns its mutable clock, materials and decorative children. Direct child `IVfxTrack` layers sample that one clock for pause, step, speed, reduced motion and release. Sprite, textured ribbon and bounded particle tracks may coexist in an effect; shader animation does not use global `TIME`.
- Ambient orbit tracks can opt into bounded angular rhythm and vertical bob, both zero by default and sampled analytically from that same clock. Reduced motion freezes both. The stun scene owns its tighter head-relative composition and distinct star/scroll artwork. Jet flame artwork faces +X and uses its own local tail shader; upright burn artwork keeps its tip at the top and retains its existing motion ownership.
- Each invocation snapshots immutable `VfxPlaybackParameters`: CastSpeed, MotionSpeed, optional FlightDuration, ParticleScale, Density and WidthScale. Cast speed scales authored charge, ribbon sweep and opted-in fragment birth delays; ribbon tail and impact/outro remain on real local seconds. MotionSpeed drives persistent internal motion without changing state lifetime or release. Flight duration is independent of cast speed. The player's global speed/pause still applies to every local clock. Definitions declare CastDuration, FlightDuration and ActionSpan so slow casts extend lifetime rather than losing their tails; shared resources never store resolved hero rates.
- `VfxPlaybackState` supports Automatic timing for standalone playback and Events timing for authored cast/flight sequences. Battle sequence cues require a unique invocation/projectile InstanceId and carry start, fired, progress, impact and end facts. Event timing never predicts impact from elapsed visual flight; repeated/late fired or impact cues do not restart phases, and end cancels pending phases. Endpoints, radius and normalized flight progress can update live; playback rates and particle counts remain birth snapshots. Producers own event ordering and progress. There is no independent gameplay cast-speed attribute yet: this adapter accepts explicit resolved rates, does not reinterpret AttackSpeed, and is not an automatic binding of every hero skill.
- Range-aware definitions (Ground or UsesRadius) use ReferenceRadius to compensate decorative particle size while scaling area; birth counts grow with reference area and Density, capped at 48 ballistic or 64 ambient particles per layer. UsesRadius is independent of ground anchoring. Orbit star counts remain authored. Changing a live radius does not rebuild the particle pool; replay with new parameters to change allocation. ParticleScale changes supported emitter particles independently; WidthScale changes stretched beam width independently of source/target distance. These controls are consumed by relevant tracks, not a promise that every layer supports every parameter.
- Spatial tracks receive context, stage projection and the stage-to-instance transform explicitly through IVfxSpatialTrack. VfxSweepPlane follows Source and snapshots the optional Direction (otherwise Target minus Source) at the first sample. It constructs the forward half-disc in the world plane before projection, so direction and radius remain independent of target distance and screen flattening. VfxSectorTrack owns a static 180-degree mesh with angular reveal and independent per-segment tails; cast speed scales the sweep, not tail duration. Arc fragment emission can distribute birth times along that same sweep and offset velocity tangentially. These are shared visual authoring capabilities, not a new gameplay cleave binding.
- Ribbon geometry follows an authored `Curve2D`; source textures provide material detail. Fragment emitters instantiate bounded authored sprites and use presentation-local randomness and analytic motion. These decorative nodes never determine projectile collisions or damage.
- `VfxAmbientTrack` owns a bounded pool of authored particle scenes per layer. Drift, radial, cone and orbital motion share the instance clock; sustained emitters wrap each particle only at its invisible birth/death boundary, rather than restarting the emitter. Local seeds support deterministic visual checks without consuming battle RNG. Orbit layers can opt into phase offsets, continuous near/far scale and gentle tilt (all zero by default); reduced motion freezes these poses as well as trajectories, while preserving a cone's range silhouette. Instance release and scope cleanup own all particles.
- Ambient layers can opt into analytic drag and screen-up acceleration (both zero by default). Buoyancy is transformed into emitter space so rotated/nonuniformly scaled jet effects still rise on screen; velocity-facing sprites use the resulting tangent plus their authored texture-axis offset. These are decorative motion parameters, not a fluid simulation or gameplay projectile physics.
- The shared catalog contains offensive, elemental, status, restoration and summon samples. `PreviewNote` describes what to observe; `ReactsToImpact` declares whether hit/break preview controls are meaningful. `UsesWidth` enables width controls for spatial links whose endpoints are projected independently, while `StretchBetween` also declares that capability. The catalog does not imply gameplay bindings: new samples remain independently playable content until an ability or status explicitly references them.
- `VfxSubEffectTrack` composes a finite automatic visual pattern from leaf definitions, with explicit stage/context injection, cast-relative offsets in time and logical-area offsets in space. A spawned child's position is a birth snapshot, its flight duration stays authored, and its particle/rate parameters inherit the invocation. Parent lifetime must include the last child's tail. Nested patterns, persistent children and event-driven parent playback are rejected; cancellation suppresses pending births and ends active children. This is visual choreography, never a source of targets, collisions or hit facts.
- Source-centered thrust/whirlwind tracks reuse the world-plane projection contract, with locked heading and independent real-time segment tails. Spatial link tracks connect actual source and target, keeping endpoint/particle sizes separate from beam length. Root growth holds authored curves; frozen crystals retain their formed body until release; healing fields project their ground footprint and emission origins while keeping rising signs upright. A vortex uses the same projected cross-section for its funnel and skirt, with independent surface flow and bounded particles. These instance-owned tracks are content authoring capabilities, not gameplay operations.
- Orbital tracks use an instance-owned static strip mesh and clock-driven shader projection, with separate front/back passes around a stable body. Radius, plane, speed, arc length and tint are authored in component instances; no geometry is rebuilt per frame. Radial particle emission is a presentation option of the same bounded analytic fragment emitter.
- `VfxTimedGroup` samples authored child tracks after a local cue delay; cancelling before that cue prevents it from starting during release. Source-aware tracks receive the projected source and local unit scale explicitly through `IVfxSourceTrack`. `VfxFallingTrack` now samples a ballistic lob, tangent orientation and historical trail positions from the same instance clock; projectile size and arc height are independent of blast radius. Ground-anchored mixed air/ground effects can disable definition-level `FlattenGround` and flatten only their authored impact group. These tracks are presentation-only: the `firefall` catalog sample is not a gameplay projectile or an ability binding, and cannot apply area damage. Formal integration must use cast/landing facts rather than delaying a damage-result cue by the sample's flight duration.
- The current `RangedAttackLayer` is a compatibility adapter for ranged facts, typed ability VFX and shield lifetime facts. A damage-result cue starts impact presentation immediately; visual stroke delays cannot defer damage or imply new hits. Generic Status VFX reconstruction is still incomplete and must not be assumed from the presence of authoring fields.
- A committed mana skill's single `ability` fact carries the compiled presentation `CastVfx` as `SourceVfx`; the presentation adapter starts that catalog effect, falling back to `spell_cast` when unspecified. HC20 binds `cast_blood` and HC18 binds `cast_mend` in their independent ability resources. This source feedback is independent of recipient count, basic healing and passive triggers; it does not invent windup time or delay resolution. Source/tick ownership prevents duplicate concurrent playback, follows visible body movement, and ends on expiry, source defeat or battle replacement/teardown.
- Body-covering effects receive an optional immutable `VfxBodyVisual` snapshot through an explicit resolver injected by the battle composition root. It contains the current sprite texture, stage-local transform, offset and facing. `VfxBodySurfaceTrack` aligns a separate Sprite2D to that sample and normalizes atlas UVs; its material is instance-owned and never replaces or modifies the unit material. Preview definitions may select source placement and original actor frames; preview samples idle, overlay and single-step on the shared clock. Preview and battle use the same catalog, scene and player.
- Basic healing emits the ordinary `attack` animation cue on its `heal` fact; it does not request an active-skill pose. `UnitAnimationComponent.UseNeutralSkillFallback` is an opt-in content-scene setting for missing cast clips (currently HC18 and HC20): native `skill_cast`/`cast` clips retain precedence; otherwise an authored-speed idle pose accompanies source VFX. This neutral pose replaces stale queued actions and yields immediately to the next actual action, without altering healing, mana, recovery or attack cadence.

## Catalogs And Loading

- Stable ids exist only on definitions. A catalog entry owns exactly one `PackedScene` plus the same definition resource referenced by that scene root; it does not repeat the id or store a scene path in the definition.
- An id-to-entry registry is allowed for lookup. Concrete-id behavior dispatch is forbidden.
- Stable ids are ASCII and are the save-game and cross-reference keys.
- Human-facing scene/resource filenames and display names use Chinese where practical.
- Missing ids, scenes, definitions, or required components fail visibly with low-noise diagnostics. There is no silent placeholder for core content.
- Content discovery and validation happen before a run begins; combat hot paths do not scan directories.
- Catalog validation is bidirectional: every catalog entry must match one concrete content scene on disk and every concrete content scene must appear exactly once. Ids, scene references, and definition references are unique.
- Unit and item content roots expose authoring validation plus explicit bind/activate/deactivate lifecycles. A bare host can add any concrete scene to the tree and process a frame safely without a game root.
- Registry creation owns one scoped engine logger across the entire pipeline: it installs before catalog/structural validation performs its first scene instantiation, remains active through the batched hidden-host ready/process pass and all cleanup, and is removed only after captured errors are merged. First-pass structural instantiate/free plus ready-pass instantiate, attach, ready, process, detach, exit, and free errors all reject Registry publication, including errors that report without throwing or occur only once.
- Activation receives an explicit binding context for the Battle-local typed event pipeline, seeded randomness, command submission, and modifier registration. Content must not discover `/root`, `CurrentScene`, groups, parent chains, or cross-root `NodePath`s.
- Equipment and Relic effects register and unregister symmetrically. Mutable ownership, stacks, charges, counters, and rolls live in explicit Run/Battle instance state, never item, Equipment, or Relic definitions.
- Activation publication is transactional: failure restores the bound state. Deactivation clears local state before notifying collaborators, so cleanup remains stable even when an external sink fails.
- Validation returns a structured report. Any core error rejects run creation and makes headless validation exit non-zero; logging alone is not a gate.
- Cross-product authored publication validates catalog entries, independent floor-rule scenes, the complete Ability/Status/Trait/Equipment/Relic/TacticalCommand graph, and `GameProject` campaign/pool/encounter/Boss-timeline graph as one package. Any failure publishes neither a Registry, Project, compiled graph, nor non-zero publication version, and diagnostics retain the authored resource path plus binding/operation index. The production package entry point still runs the stricter bidirectional on-disk catalog gate.

## Mature Combat Build Contracts

Shared content-authoring and execution contracts (bounded expressions, selectors, source/damage identity, revocable grants, and transactional Run offers) are specified in `content-composition-foundation.md`. That module also states supported limits rather than equating schema fields with runtime capability.

### Hero Mana And Formal Equipment Integration

- `UnitDefinition` authors MaxMana, StartingMana, ManaPerSecond, ManaPerAttack, ManaPerDamageRatio and ManaPerHitCap. `BattleSetupFactory` publishes them into the existing compiled attribute set; definition/resource fingerprints include them. ManaFull is an Automatic Ability trigger, not a new parallel effect executor. Its loadout contains at most one mana skill; content publication validates a positive matching base capacity/cost and finite recovery values.
- `BattleUnitState` exclusively owns CurrentMana, ManaLockedUntilTick and LastAbilityName. `BattleHeroMana` performs capped fixed-tick/per-action/effective-damage accounting; temporary bodies have no hero mana pool. `BattleAbilityScope` retains per-owner skill cooldown/use state and delegates mana-full payment to the owner's world transaction, never its legacy shared manual budget.
- `AbilityDefinition.AutomaticTarget` compiles to an explicit policy for a legal current/near enemy or the lowest-health-ratio wounded ally. Battle resolves its explicit target before operation preflight; movement, reach and line access remain authoritative. Control gates are checked before automatic activation and again at commit. Failed preflight does not allocate mana or cast state.
- A ready automatic WoundedAlly skill with one wounded-ally Heal operation may approach a recipient when its finite owner-centered query is empty. The ability adapter reads the registered compiled skill and failed activation result, preserving tags and wound eligibility; it does not infer pursuit from arbitrary compound-condition failures. Movement receives the skill's center range explicitly instead of basic body-edge reach. Cooldown/resource failures and stationary or disabled owners do not initiate this pursuit.
- Ability operation batches, including damage/death/reaction chains, use `BattleWorldStateCheckpoint` for attributes, Statuses, Traits, Relics, unit health/mana/actions, movement, temporary units, combat/effect queues and counters, reports, death bookkeeping and append-only presentation. Each Effect binding still has one kernel step; multiple authored operations may share a transaction. A target killed by an earlier operation is skipped by subsequent inapplicable effects, not resurrected or treated as a reason to undo the kill. Genuine commit failure restores the entire checkpoint.
- A successful living mana caster publishes the presentation `ability` fact plus the typed `AbilityResolved` fact. `BattleScreenRuntimeUnitSnapshot` is read-only, includes mana/skill/equipment presentation, and resolves Chinese item data at the explicit ContentRegistry boundary. Shared health-view and inspection components never calculate gameplay.
- Formal equipment ownership (introduced in v5, retained by schema v7) stores each unique instance either in EquipmentInventory (no owner, slot -1) or in exactly one hero's three-slot Equipment. Run services clone, validate, save and publish transactions; replacement/removal return items to inventory. Supported migration requires unambiguous prior state and preserves a recoverable original; v6 adds durable decision/terminal state. Failed save never publishes ownership changes. Equipment management binds the same service in deployment and the global hero roster; rewards only grant inventory and do not host another equipment editor. Battle lifecycle explicitly locks editing.
- The old independent ExperienceSlice inventory remains isolated and its deployment disables formal equipment editing. The Web model and research corpus are unchanged. Runtime/visual checks for this integration are tracked in `work-items/active/formal-equipment-and-hero-mana.md`; compilation alone does not establish player-facing acceptance.

### Shared Build Primitives

- `BattleAttributeSet` evaluates one attribute as ordered base plus additive contributions, then multiplicative factors, then one deterministic override winner, followed by the attribute-specific clamp. Every contribution carries a stable `CombatSourceRef`, source-instance identity, and application order; authoritative removal by handle/source restores the exact remaining projection. Typed magnitudes cover constants, source/target attributes, invocation context, named team counts, and trait values with explicit snapshot-versus-live capture.
- Status/Modifier definitions own instant/timed/permanent duration, aggregation-by-source/target/independent policy, stack/overflow behavior, duration refresh, periodic reset, dispel category, death policy, granted state tags, sourced attribute modifiers, lifecycle/reactive bindings, and immutable presentation. Runtime identity includes definition, source, owner, application sequence, stacks, timing, and captured magnitudes; multi-source target aggregation is representable. Typed disposition is `Neutral`, `Helpful`, or `Harmful`; exact-id/source dispel remains available while owner-wide purge may filter by disposition and ordinary/strong strength, and `NonDispellable` always survives purge.
- Action authority queries typed state tags. For timed control using `LinearResistanceCeiling`, effective duration is `max(1, ceil(authored_ticks * (1 - clamp(ControlResistance, 0, 1))))`; removal, expiry, dispel, death, and scope teardown reverse all sourced contributions idempotently.
- Active Status combat reactions subscribe only to attack declared/landed, Ability resolved, damage/healing/shield resolved, or unit defeated/killed facts. `OwnerIsSource` matches the event source and freezes the event target as the explicit counterpart; `OwnerIsTarget` matches the event target and freezes the event source as the explicit counterpart. The immutable invocation also preserves the complete typed event and uses its `EffectiveValue` as invocation magnitude. A target-aggregated multi-source Status owns one subscription per compiled binding, attributes execution to its deterministic `PrimaryContribution`, and transfers that attribution without replacing the subscription when the primary source is removed. Listeners enqueue through the Battle reaction sink and never execute gameplay synchronously inside event publication.
- Scope completion removes modifiers and subscriptions before callbacks, emits immutable `ScopeCompleted` Removed lifecycle facts and presentation cues, but deliberately suppresses gameplay Removed bindings because the Effect scope is already terminal. Cleanup or callback failures leave every Status removed and every subscription detached, then publish an `Exception` Status transition; normal completion retains its requested reason.
- `TraitDefinition` owns typed contributions/counting policy and ordered breakpoint ranges with attribute modifiers and revocable Status grants. One team-level Battle trait scope derives a contribution snapshot, removes the old tier source, and applies exactly one new tier source through shared primitives. Team/member targeting also refreshes on recipient changes without a tier change. Temporary-unit counting, duplicate identity, deployment-only counting, and extra contributions are data policies; trait value `30` never implies thirty bodies.

It retains one ordered persistent hero roster, current/effective population sources, per-hero equipment instances, exact formation cells, legacy tactical-command ids and Run-level Relic instances. Version 3 describes the former starting-hero/soldier format, not an outstanding instruction to design the next schema.
- Historical v2/v3 roster migration derives current population as at least the authored compatibility initial population or the migrated roster count when higher, but never above the ordinary cap `10`; an over-cap legacy roster is rejected instead of truncated. These preservation conditions are necessary, not a guarantee that every legacy save is supported by v7: pending-decision ambiguity and the explicit support boundary in `content-composition-foundation.md` can require rejection. Never silently drop a roster member, item, equipment owner, formation, population capability or mutable fact, or erase valid Meta/Settings.
- Save and migration contracts use isolated test namespaces. Tests never load, migrate, overwrite, or delete the player's default active-run path.

## Donor Boundary

- `D:\godot\rpg` is read-only and never referenced at runtime.
- Copy only selected unit visual packages and required license/provenance material into this repository.
- Reuse `SpriteFrames` and the active animation cue vocabulary (`idle`, `move`, `attack`, `skill_cast`, `displaced`, `defeated`). Legacy `hit` frames may remain in assets but are not played; damage facts still drive non-animation feedback.

- Units missing required cues are either excluded from the Alpha or receive an explicitly validated fallback.

## Legacy 成长 Tower 选敌与共用法术契约（2026-09-30）

`EncounterCompositionDefinition` 保存完整敌阵、适用层范围、压力摘要及额外金币／研究／材料；`EncounterDefinition.OpponentChoiceCount` 启用具体候选。`TowerGenerator.OpponentOptions` 以种子／层数／节点类型稳定洗牌并绑定实际地形，不读取玩家阵容。新增的仅选敌模板通过 `OpponentChoiceOnly` 排除旧遭遇抽取，保持旧已选战斗的随机序列。

`TowerGenerator.SelectableOpponentOptions` 仅对新精英挑战返回可选机会；原`OpponentOptions`保留普通候选确定性解析，供已锁旧档恢复／结算。`RunApplication.CurrentOpponentOptions`是只读的新机会查询，新普通战直接锁定原确定性遭遇，拒绝传入候选ID。`OpponentChoicePanel` 使用预制候选卡和单位详情，浏览与返回没有保存权威；`TowerScreenController.OpponentSelected` 经 `GameFlowCoordinator` 提交合法候选ID。`SelectNode` 在同一保存事务内设置节点与 `SelectedOpponentOptionId`，整备、冻结、战斗收据匹配及胜利奖励都从该计划读取。候选额外奖励与既有奖励／成长结算共同提交，保存失败保留原状态，败战不给额外奖励，推进后清空选择。

Active Run 当前为 v11；本节的 v8／v9／v10 语义在选定完整 legacy profile 后迁移保留。载入v8及更早已待战的成长普通／精英节点时设置`LegacyPendingOpponent`，沿用原确定性遭遇且不给新增候选奖励；旧v9已锁普通选择继续解析原计划及收益，新精英待战必须有合法候选ID，新普通战允许空ID。迁移标记与空ID、待战类型必须一致，节点推进后清理。Alpha与Boss不要求候选ID。

`BattleIdentity.CompositionId` 由正式准备写入并在结算时匹配，不能以同一EncounterId下另一候选的战果套领所选奖励。成长开战同样核对完整敌阵与地形，错误计划不能提前消费或冻结。

启用成长规则时，`RunBattlePreparationService` 不投影战术指令，正式模拟中没有可施放槽位或战术点；Alpha准备保持。旧保存中的指令ID为兼容保留，成长军团页不展示其操作规则，战斗HUD只在存在实际槽位时显示。

战前法术继续由 `GrowthRunService` 负责研究兑换、库存、预设和开战一次消费；冻结快照保存消耗法术及目标。整备页的预制“战前法术”按钮经类型化事件直达既有工坊，仅成长征程显示，并沿同一可编辑状态控制。内容通过静态能力／loadout资源投影到正式 `BattleSimulation`，破阵复用普通伤害，压制复用带到期移除的属性修饰。预览和取消不消费；保存失败、开战重试和重载均不得重复消费。

## 全局庭院背景（2026-10-01）

`CourtyardBackdrop.tscn` 组合正式 `SunlitCourtyard` 与顶部／底部阅读渐变，由五个应用入口预先实例化。根背景覆盖完整视口，不随 `ScreenRouter` 的常驻栏占位缩进；页面切换不重建它或重置空闲光照时间。路线／奖励／招募／商店沿用根背景，不再添加局部整页暗罩。输入、文字和卡片仍由原页面负责。

`AppScreenHost` 与独立 `ExperienceSliceRoot` 在显示战斗时隐藏根背景，战斗实例继续消费既有暂停／变速时钟，退出战斗后恢复根背景。地面／空气材质仍按实例隔离，装饰不读写业务状态。正式应用的减弱动效设置经已有 `UiMotionBinding` 注入。全局接入不改变页面导航或存档语义。

天气扩展也属于该展示组件：`WeatherPresentationStyle` 是只读美术配方，`RainyCourtyard`、`SnowyCourtyard`、`StormCourtyard` 是可独立打开的预制变体；`SetWeatherStyle` 接收明确的样式资源，`Advance` 只接收表现时间。地表、太阳空气与天气材质各实例私有，共用时钟和减弱动效状态。雨滴／水花配对、湿地、薄雪和云闪均在背景内部计算，不引用模拟、局内状态、寻路、碰撞或存档。`EnvironmentPreview` 复用同一生产资源；`GameRoot` 只绑定菜单导航。正式默认晴天，本轮没有业务天气或全局天气偏好。资源参数和来源见[天气说明](../scenes/environments/weather/README.md)。

## Verification Contracts

- Every cataloged unit, item, and tactical-command scene loads and instantiates in isolation.
- No content behavior contains a central switch keyed by a concrete hero, enemy, temporary-unit, equipment, relic, trait, status, or tactical-command id.
- Shared definitions remain unchanged when two runtime instances mutate state independently.
- A deep definition fingerprint remains identical after two-instance mutation, battle resolution, and save round-trip.
- Fixed-tick seeded combat produces a stable digest including continuous spatial facts and resolves without any presenter attached. Spatial planning and position restore with failed transactional commits.
- Contract coverage proves source-attributed Attribute rollback, typed attack/Status/death event ordering and non-reentrancy, mature Status aggregation, Trait tier replacement, hero-owned three-slot Equipment isolation, Reactive Relic counter reset, unified population `10/18`, two-slot/three-point tactical atomicity, and the production Frost/Freeze vertical slice.
- Every Battle termination path reports zero retained combat-pipeline subscriptions, queued reactions, sourced modifiers, Status/Trait/Equipment/Relic projections, tactical points, or presentation cues.
- Source guards reject concrete-id behavior branches and forbidden global scene-tree discovery.
- Headless UI smoke covers every authored screen, while three deterministic build paths complete the tower.
- A seeded headless run can progress from hero selection through the final result.
- Core/payoff, engine/enabler, functional/bridge, population, and no-temporary-unit formations each retain at least one validated path without requiring every hero to be a build core.
- Low-concurrency .NET build, content validation, save round-trip, and Godot headless smoke tests pass before handoff.
